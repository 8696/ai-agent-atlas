# 07-c · 模块 · 记忆与会话（模块 07-09）

> AI 模块规格。需求侧见 [12-d](./12-d-需求-记忆与配置.md)。

---

## 模块 07 · 会话与消息

**职责**：会话的增删改查 + 消息的落库与读取。

**数据**：`sessions` / `messages` 表

**关键约束**：

- 消息落库**两个字段**：`content`（纯文本）+ `parts`（JSON，结构化 part）
  - ⚠️ **parts 是「刷新后卡片还在」的依据** —— 前端渲染工具卡片读的是它
  - ⚠️ **落库的 parts 与推给前端的必须同源**（否则刷新后卡片内容会变）
- 消息写入时机：**一轮结束时**（不是一个 part 一个 part 写），
  ⚠️ **先图状态后消息**（宁可重复一条消息，也不要丢图状态）
- 标题：首条用户消息截断（≤ 30 字）
- 删除会话 → **级联删** 消息 / 工具流水 / 检查点（不留孤儿行）
- 列表排序用 `last_active_at`（冗余字段，避免列表页 N+1）

**降级**：DB 写失败 → 记录错误但**不中断已生成的回答**（内容先返回给用户）。

**已知边界**：

- ❌ 不做消息编辑
- ❌ 不做会话分享 / 导出（可后续加导出为 Markdown）
- ❌ 不做全文检索（只搜标题）

## 模块 08 · 会话摘要压缩

**职责**：长会话超出 token 预算时，把早期轮次折成摘要。

**触发**：历史 token 数 > `summary_token_budget`（或消息条数超阈值）

**关键约束**：

- **边界标记**：`sessions.metadata.summary_boundary` 记「摘要覆盖到哪条消息为止」
- 下一轮**按边界把历史切成两段** —— 边界之前**不再喂原文**
  （否则原文 + 摘要两种说法并存，模型会摇摆）
- **滚动重写**：输入是「旧摘要 + 新丢掉的轮次」，输出是一份**全新的完整摘要**
  （不是追加 —— 追加会越滚越长且矛盾）
- 摘要**另起一条 trace**（`kind='summary'`），⚠️ **不挂在对话 trace 上**
  （对话 trace 的 duration 必须保持「用户感知耗时」）
- 摘要模型走 `usage_scope='summary'`，回落链「摘要模型 → 对话模型 → 平台默认」
- 摘要开关 `summary_enabled`（关掉则退回复制「截断」）

**降级**：

| 情况             | 行为                                       |
| ---------------- | ------------------------------------------ |
| 摘要调用失败     | 退回「截断」（按预算保留最近 N 条）        |
| 摘要写入失败     | 边界不推进（下轮重试）                     |
| 进程在写完前被 kill | 这段摘要丢失（下一轮重来）                |

**已知边界**：

- ⚠️ **摘要滞后一轮**：本轮丢掉的轮次要到下一轮才进摘要（fire-and-forget）
- ⚠️ **摘要有损**：模型改写过的内容跟原文不完全一致，细节可能丢
- ⚠️ **长对话每轮可能多一次 LLM 调用**（可关 / 可配便宜模型）
- ⚠️ **摘要在 system prompt 里不是消息**（语义上略差，检索型问答影响不大）

## 模块 09 · 长期记忆

**职责**：记住「关于这个用户的事实」，跨会话召回，并允许用户查看与删除。

**数据**：`memories` 表（内容 / 类型 / 来源 / 置信度 / 状态 / 向量 / embedding 模型）

**三级更新机制**：

| 级别 | 做法                                                             | 成本     |
| ---- | ---------------------------------------------------------------- | -------- |
| T1   | 正则信号预筛（「记住 / 我喜欢 / 我叫 / 我用 …」）                | 零       |
| T2   | 调 LLM 抽取（把现有记忆一起喂进去，模型决定新增 / 改写 / 归档）    | 一次调用 |
| T3   | 用户手动改                                                       | 零       |

**关键约束**：

- **一条记忆 = 一条事实**（不存长文本）
- 注入走 system prompt，排在检索资料段**前面**
- ⚠️ **冲突时以工具返回的事实为准**（记忆是「偏好」，不是「世界事实」）
- **召回排序**：相关性为主序，优先级（来源 > 置信度 > 更新时间）为兜底
  - ⚠️ **没有向量的记忆按 0 分算**（与「有向量但不相关」同档）——
    不会被「缺向量」饿死，但也没法靠相关性排上来
- **每轮 top N + token 预算双重裁剪**
- ⚠️ **抽取模型可独立配**（`usage_scope='memory'`）——
  推理模型的思考 token 全额算输出（实测 2000+），
  配条便宜模型是唯一能压成本的手段

**降级**：

| 情况                   | 行为                                      |
| ---------------------- | ----------------------------------------- |
| embedding 服务挂 / 没配 | 退回固定顺序（按时间倒序），**对话不受影响** |
| 抽取调用失败           | 忽略这一轮（对话照常）                   |
| 向量库扩展加载失败     | 进程内线性扫描；再失败则退回固定顺序      |
| 写入向量失败           | 业务库照写（权威副本），标记「待补算」    |

**已知边界**：

- ⚠️ **抽取是 fire-and-forget**：对话结束几秒后记忆才落库，
  「刚说完就立刻追问」那一轮用不上新记忆
- ⚠️ **抽取没有跨实例锁**（本地单实例不构成问题）
- ⚠️ **只能改得动「最近 50 条」记忆**（模型的目标 id 取自喂给它的快照）
- ⚠️ **没有遗忘机制**：只增不减，靠 50 条上限 + 冲突时归档收敛
- ⚠️ **「本轮用了哪几条记忆」查不到**（注入结果没回传前端）
