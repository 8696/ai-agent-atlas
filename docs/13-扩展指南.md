## 13.2 怎么新增一条需求

### 命名约定

```
<字母类>-<序号> · <一句话需求名> · <P0|P1|P2>
```

- 字母类：`A` 应用外壳 · `B` 对话与编排 · `C` 工具与扩展 · `D` 记忆与配置 · `E` 观测安全
- 序号在该类内递增，**不回收**（删掉的编号留空，不复用）
- 优先级：`P0` 系统跑不通 / `P1` 缺了就是原型 / `P2` 增强项

### 新增需求模板

```markdown
## <X><n> · <需求名> · <档位>

**需求**：<一句话说清要做什么，面向用户>

**技术要求**：

- <约束 1：这条需求对实现的技术要求，不是实现细节>
- <约束 2：⚠️ 坑 / 边界>

**验收**：

- [ ] <可验证的行为 1>
- [ ] <可验证的行为 2>
```

### 同步清单（新增需求时**四件事都要做**）

1. 需求正文 → 对应的 `12-x` 文件
2. **状态表** → [12-e §E5](./12-e-需求-观测安全与验收.md) 的总表加一行
3. [01 §1.6](./01-需求与场景.md) 的需求清单表（条数变了要改）
4. 涉及数据表 → [05-a](./05-a-数据模型-sqlite.md)；涉及 UI → [04-x](./04-a-ui-总则布局与菜单.md)

### 示例：加一条「B9 · 文件夹监听」

```markdown
## B9 · 文件夹监听 · P2

**需求**：用户指定一个目录，Agent 在文件变化时被唤醒并总结变化。

**技术要求**：

- 监听实现用 `fs.watch`（⚠️ **不保证完整覆盖**：部分平台对子目录的变化不触发，
  需要递归监听时得自己加轮询兜底）
- 监听目录必须在 `workspace_root` 内（复用路径沙箱判定，不另开一套）
- 变化事件**去抖**（默认 1 秒窗口合并一批），避免编辑器保存一次触发几十次
- 唤醒走「后台触发一轮对话」—— ⚠️ **这条路径没有用户输入**，
  要复用图但不能走「等用户确认」的分支（有危险工具就跳过并记录）

**验收**：

- [ ] 在监听目录里新建文件 → 1 秒内产生一轮总结
- [ ] 监听目录外的路径被拒绝
- [ ] 一次批量保存只触发一轮（去抖生效）
```

## 13.3 怎么新增一个 AI 模块

### 模板

```markdown
## 模块 <NN> · <模块名>

**职责**：<一句话>

**输入**：<参数>
**输出**：<返回>

**关键约束**：

- ⚠️ <最容易被违反的那一条>

**降级**：

| 情况     | 行为   |
| -------- | ------ |
| <失败点> | <兜底> |

**已知边界**：

- ⚠️ <用户会踩到的边界>
- ❌ <明确不做的事>
```

### 模块编号

| 范围  | 内容                             | 归属文档 |
| ----- | -------------------------------- | -------- |
| 01-03 | LLM 与 Prompt                    | 07-a     |
| 04-06 | 工具与 Skill                     | 07-b     |
| 07-09 | 记忆与会话                       | 07-c     |
| 10-12 | 编排（图 / 工具节点 / 事件翻译） | 07-d     |

新增模块 → 在对应 `07-x` 文件末尾追加，**编号顺延，不重排**。

## 13.4 怎么加一个工具

1. 在 `src/tools/builtin/` 实现（内置）或 `src/tools/skill/`（技能自带）
2. **声明敏感档**（`low` / `normal` / `high`）——
   ⚠️ **不确定就往严了判**：`high` = 要人确认
3. 在 `src/tools/registry.ts` 注册（名称唯一）
4. **路径 / 出网 / 命令**类工具**必须走 `lib/security/` 里的闸**
   ⚠️ **不许自己写一套检查**（各写各的必然漏）
5. 补一条 `tool_call_logs` 的状态（如果有新状态）
6. 文档：
   - [07-b 模块 05](./07-b-模块-工具与skill.md) 加进清单
   - [12-c C2](./12-c-需求-工具技能与扩展.md) 更新工具表
   - [10](./10-安全方案.md) 评估是否新增威胁
7. 测试：越界用例必须有（路径逃逸 / 内网地址 / 黑名单命令）

## 13.5 状态追踪

需求状态写在 [12-e §E5](./12-e-需求-观测安全与验收.md) 的总表里：

| 状态                | 含义                                         |
| ------------------- | -------------------------------------------- |
| 待实现              | 还没开始                                     |
| 进行中              | 写了没做完                                   |
| 已实现              | 代码落地 + 测试通过 + 文档同步               |
| 已实现 · 有已知边界 | 落地了，但有明确的已知限制（要在文档里写清） |

> ⚠️ **状态不能只写在代码里** —— 文档里的状态表是唯一权威。
> ⚠️ **「已实现」必须有验收清单打勾**，不是「我觉得写完了」。

## 13.6 文档版本约定

- 文档顶部不放版本号（避免每次改都要动一堆）
- **改动历史写在文件末尾的「变更」小节**（格式见 §13.8.2）
- 大改（推翻原设计）→ 在变更记录里写清「为什么推翻」，
  ⚠️ **不要静默改掉旧结论**（后来的人会想知道当初为什么那么定）

## 13.8 变更同步规则（**最重要 · 文档 = 系统规格**）

### 13.8.1 改 X → 必须同步改 Y（按场景分）

| 你改了                   | 必须同步                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------ |
| **工具的行为**           | `07-b` + `12-c` +（如果是危险能力）`10`                                                    |
| **模型的用法**（图结构） | `03-b §B.5` + `07-d` + `12-b`                                                              |
| **数据表**               | `05-a`（⚠️ 同批改迁移）                                                                    |
| **配置项**               | `.env` + `.env.example` + `src/config.ts` 的 envSchema + `12-a A5`                         |
| **页面 / 交互**          | `04-x`（⚠️ **先改规格再改代码**）                                                          |
| **提示词**               | `06 §6.4`（组装顺序）                                                                      |
| **安全边界**             | `10`（威胁模型 + 三道闸）                                                                  |
| **新增能力**             | `01`（Out of Scope 要相应放开）+ `12-x`（⚠️ **按三段式补成一条正式需求，并打上状态徽标**） |
| **删掉 / 砍掉能力**      | `01 §1.5`（**从「不做」里拿掉**）+ `12-e` 状态表                                           |

### 13.8.2 变更检查清单（每次改东西必走）

```markdown
## 变更 [日期] · [一句话描述这次改什么]

### 改了哪里

- src/...：<改了什么>
- web/...：<改了什么>
- docs/...：<同步改了哪几份>

### 验证

- [ ] yarn run check（typecheck + lint）
- [ ] yarn test（<跑了哪些>）
- [ ] 手工验证：<怎么确认>

### 遗留

- <还没做的，明确写出来>
```

> ⚠️ **「遗留」不能空着就不写**。
> 没做完的事要写出来 —— 藏在「已完成」里比没做更危险。

### 13.8.3 文档 ↔ 代码对照（快速验证两边一致）

加**机械守卫测试**，比人肉核对可靠：

| 要守的不变量        | 怎么守                                              |
| ------------------- | --------------------------------------------------- |
| 工具清单一致        | 扫 `src/tools/builtin/` 的文件名 → 对照 `12-c` 的表 |
| 配置项数量一致      | registry 的条数 → 对照 `12-a A5` 的数量             |
| 需求编号连续无重复  | 扫 `12-x` 的标题 → 断言编号集合与 `12-e` 状态表一致 |
| 路由 ↔ 页面清单一致 | 扫 `web/routes.tsx` → 断言与 `03-c §C.3` 一致       |
| env key 一致        | `envSchema` ↔ `.env` ↔ `.env.example` 三方一致      |

> ⚠️ **改了代码忘了改文档，守卫测试要能红**（这才是它的价值）。
> 写完守卫测试后**做一次扰动验证**：把数字改回旧值，确认测试确实会失败。

### 13.8.4 「文档先行」原则

- **改 UI 前** → 先改 `04-x` 规格，再改代码
- **加需求前** → 先写 `12-x` 的「需求 + 技术要求 + 验收」，再写代码
- **改表前** → 先改 `05-a`，再写迁移
- ⚠️ **原因**：规格是「为什么这样」，代码只是「怎么这样」。
  只改代码的话，三个月后没人知道当初为什么这么设计，
  于是「顺手改一下」就会把设计改坏。

## 13.9 命名 / 格式约定

| 对象        | 约定                                        |
| ----------- | ------------------------------------------- |
| 文件名      | kebab-case（`knowledge-routes.ts`）         |
| 组件名      | PascalCase（`ToolCallCard.tsx`）            |
| 函数 / 变量 | camelCase；布尔用 `is` / `has` / `can` 前缀 |
| 常量        | UPPER_SNAKE（`MAX_TOOL_STEPS`）             |
| 数据库表    | 复数 snake_case（`tool_call_logs`）         |
| 迁移文件    | `NNN-描述.ts`（编号递增，不重排）           |
| 环境变量    | UPPER_SNAKE                                 |
| 需求编号    | `<字母类><序号>`（见 §13.2）                |
| 模块编号    | `NN`（两位，见 §13.3）                      |
| 审计 action | UPPER_SNAKE（`MODEL_CREATED`）              |
| part 类型   | `data-<kebab-case>`（`data-tool-call`）     |

**Markdown**：

- 标题用 `##` / `###`（一个 `#` 只用一次）
- 表格用于结构化对比，⚠️ **不要用表格装长段落**
- ⚠️ **重要结论前面加 ⚠️**（这是本项目的既有风格，用于标记「这里有个坑」）
- 代码块标语言（`ts / `bash / ```json）
- 相对链接引用其他文档（`./12-a-需求-应用外壳与上下文.md`）

## 13.10 协作模式

> **口头指令 > 文档**。文档是参考，指令是命令。

| 情况             | 做法                                                                     |
| ---------------- | ------------------------------------------------------------------------ |
| 指令明确         | 照做                                                                     |
| 需求边界有歧义   | **先问**，不要自己拍板                                                   |
| 涉及表结构变更   | 先说清要加什么列、为什么，再动手                                         |
| 涉及跨模块影响   | 先列方案再动手                                                           |
| 涉及删除既有代码 | 先确认再删                                                               |
| 改完代码         | 停服务 → 跑相关测试 → 按 **HIGH → MEDIUM → LOW** 列发现 → **停下等指令** |
| 没派活           | **不主动挑需求、不主动加功能、不主动换技术栈**                           |
