### A.3 TypeScript 配置（两个 project + 一份构建配置）

> ⚠️ **project 的数量直接决定 lint 速度** ——
> 类型感知规则要为每个 project 建一份 TS Program，
> 每份都要重新解析 `lib.*.d.ts`（很贵）。实测（42 个文件）：
>
> | 形态                           | `yarn lint` |
> | ------------------------------ | ----------- |
> | 只查语法（不给类型信息）       | ~0.9s       |
> | 4 个 project                   | ~4.3s       |
> | **2 个 project（现在的结构）** | **~3.6s**   |
>
> 所以**能合的就合** —— 但前后端必须分开
> （`jsx` / `DOM` vs `types: ["node"]`）。

**① `tsconfig.json` —— 后端 + 测试 + 根级构建配置**

```jsonc
// tsconfig.json
{
  "compilerOptions": {
    "target": "ES2023",
    "module": "ESNext",
    "moduleResolution": "bundler",
    // ⚠️ DOM 是给 e2e 测试用的（Playwright 页面类型）——
    //    合并成一个 project 后，后端也会看到 DOM 全局量（只多类型，不报错）
    "lib": ["ES2023", "DOM", "DOM.Iterable"],
    "strict": true,
    "exactOptionalPropertyTypes": true,
    "noUncheckedIndexedAccess": true,
    // ⚠️ **模型不用装饰器了** —— 装饰器要靠这两个选项才能编译，
    //    而 tsx 是**按 cwd 找 tsconfig** 的，从别的目录启动会直接编译失败
    //    （见 [12-a A1](./12-a-需求-应用外壳与上下文.md)）
    //    留着这两项无害，但**别再往里加装饰器**。
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "outDir": "dist",
    "rootDir": ".",
    "types": ["node"],
  },
  "include": [
    "src/**/*",
    "shared/**/*",
    "scripts/**/*",
    "tests/**/*",
    "vite.config.ts",
    "vitest.config.ts",
    "playwright.config.ts",
  ],
}
```

**② `web/tsconfig.json` —— 前端（extends 根上的基座 `tsconfig.web.json`）**

```jsonc
// web/tsconfig.json
{
  "extends": "../tsconfig.web.json",
  "include": ["**/*"],
}
```

**③ `tsconfig.build.json` —— 构建用（只编译要发出去的东西）**

```jsonc
// tsconfig.build.json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    // 后端本来就没有 DOM —— 构建时还原成后端那套 lib
    "lib": ["ES2023"],
  },
  "include": ["src/**/*", "shared/**/*", "scripts/**/*"],
}
```

> ⚠️ **`web/tsconfig.json` 不是冗余** ——
> ESLint 的 `projectService` 是**从文件所在目录向上找「名字正好是 `tsconfig.json`」的文件**，
> `tsconfig.web.json` / `tsconfig.build.json` 它**看不见**。
> 少了它，`web/` 下的文件就拿不到类型信息 →
> 类型感知规则直接报 `was not found by the project service`。
> **加新目录时，记得给它配一份同名 `tsconfig.json`。**
>
> ⚠️ **构建用单独一份** —— 根 `tsconfig.json` 里还塞着测试和根级 config
> （供类型检查 / ESLint 用），那些**不该进 `dist/`**。

#### A.3.1 相对导入必须带 `.js` ⚠️

> ⚠️ **源码里的相对导入一律带 `.js` 后缀** —— `'./config/paths.js'`，不是 `'./config/paths'`。
>
> 原因：源码是**原生 ESM**（`package.json` 里 `"type": "module"`），
> **Node 的 ESM 解析器不做扩展名补全**：
> `'./config/paths'` 在 `tsx` 下能跑（tsx 帮它兜底），
> 但 `tsc` 编译出来的产物用 `node` 跑就是 `ERR_MODULE_NOT_FOUND`。
>
> TypeScript 会把 `./x.js` 自动映射到源码的 `./x.ts`，
> 所以**写 `.js` 完全不影响开发**（`tsx` 也认这个映射）。
>
> ⚠️ **这就是 `yarn start` 之前跑不起来的两个原因之一**
> ——另一个是产物路径（`dist/server.js` vs 实际的 `dist/src/server.js`）。

### A.4 ESLint（flat config，前后端共用一份）

```js
// eslint.config.js
import js from '@eslint/js';
import tseslint from 'typescript-eslint';
import globals from 'globals';

export default tseslint.config(
  { ignores: ['dist/**', 'dist-web/**', 'node_modules/**', 'data/**', 'logs/**', 'backups/**'] },
  js.configs.recommended,
  {
    // ⚠️ **类型感知规则只给 TS/TSX** ——
    // `recommendedTypeChecked` 里的规则要类型信息，
    // 而 `eslint.config.js` 这类 .js 文件没有类型信息 → 规则直接抛错。
    // 所以整组配置（含 parser）都限定在 TS 文件上。
    files: ['**/*.ts', '**/*.tsx'],
    extends: [...tseslint.configs.recommendedTypeChecked],
    languageOptions: {
      globals: { ...globals.node, ...globals.browser },
      parserOptions: {
        // ⚠️ **用 projectService 而不是 project** ——
        // `project: [...]` 每个文件都新建一个 TS Program（慢）；
        // `projectService: true` 走 TS 的增量服务，自动就近找 tsconfig。
        projectService: true,
        tsconfigRootDir: import.meta.dirname,
      },
    },
    rules: {
      '@typescript-eslint/no-explicit-any': 'warn',
      '@typescript-eslint/no-unused-vars': ['error', { argsIgnorePattern: '^_' }],
      // CLI 与启动期的用户可见输出走这三个；其余 console.log 一律报警
      'no-console': ['warn', { allow: ['info', 'warn', 'error'] }],
    },
  },
);
```

> ⚠️ **为什么用 `extends` 而不是展开 `...tseslint.configs.recommendedTypeChecked`** ——
> 展开的话，那组配置会**对所有文件生效**（flat config 的 `files` 缺省 = 全部），
> `.js` 文件就会因为「没有类型信息」直接把 ESLint 干崩。
> `extends` + `files` 才能把「parser + 类型感知规则」一起收进 TS 文件里。
>
> ⚠️ **`projectService: true` 依赖「每个 TS 文件都能找到一个 tsconfig」** ——
> 查找规则是「从文件所在目录向上找**名字正好是 `tsconfig.json`** 的文件」，
> 所以 `web/` 和 `tests/` 各自有一份同名配置（见 §A.3）。
> 找不到时报 `was not found by the project service`。
> 兜底是 `parserOptions.allowDefaultProject`（给不在任何 tsconfig 里的文件用合成 project），
> ⚠️ 但合成 project 的 compilerOptions 不是你项目的那套严格配置，**优先补 tsconfig 而不是用它**。

> ✅ **`yarn lint` 现在能正常跑**（2026-10-31 修好）
>
> **当初为什么跑不起来**：`typescript-eslint@8.72` 不支持 TypeScript 7.0 ——
> TS 7 是 Go 重写版，**不发布 JS API**（`typescript@7` 的 `main` 是空的，
> `exports["."]` 只导出版本号）。typescript-eslint 一启动就读
> `require('typescript').versionMajorMinor`，主版本 ≥ 7 就直接抛
> `typescript-eslint does not support TS 7.0`。**这不是配置写错**，是上游兼容性问题
> （跟踪 issue #10940）。
>
> **修法：TS 6 与 TS 7 并存**（用户 2026-10-31 口头批准执行）——
> TS 7 只管**编译**（`tsc`），TS 6 的 **JS API** 供**工具链**用：
>
> ```jsonc
> // package.json · devDependencies
> "typescript": "npm:@typescript/typescript6@^6.0.2",  // TS 6 API（给 typescript-eslint）
> "typescript7": "npm:typescript@^7.0.2",             // 原生 TS 7 编译器（bin: tsc）
> ```
>
> 装完之后解析到的各是各的：
>
> | 谁                       | 解析到什么                      |
> | ------------------------ | ------------------------------- |
> | `node_modules/.bin/tsc`  | **TS 7.0.2**（→ `typescript7`） |
> | `node_modules/.bin/tsc6` | TS 6（→ `typescript`）          |
> | `require('typescript')`  | **TS 6.0.3 完整 API**           |
>
> ⚠️ **typescript-eslint 只认 `typescript` 这个名字** ——
> 它内部（parser / typescript-estree）到处 `require('typescript')`，
> 靠 Node 的解析规则找到顶层那个包。所以**另起一个别名装 TS 6 没用**，
> 必须让 `typescript` 这个名字本身指向 TS 6。
> ⚠️ **`@typescript/typescript6` 只提供 `tsc6` 这个 bin、不抢 `tsc`** ——
> 这样 `tsc` 仍然归 TS 7，两个版本不会在 `.bin` 里打架。
>
> **现在 `yarn run check` = typecheck 与 lint 并行**（`concurrently`）——
> lint 已进默认验证闸（见 A.8.2 的 L0 静态闸）。
> lint 已进默认验证闸（见 A.8.2 的 L0 静态闸）。

#### A.4.1 类型感知 lint（`recommendedTypeChecked`）

> ✅ **2026-10-31 启用** —— 从「只查语法」升级到「查类型」。
> 下面是这套规则真正抓到过的东西（都不是 ESLint 语法层能发现的）：

| 规则                             | 抓到了什么                                               |
| -------------------------------- | -------------------------------------------------------- |
| `no-misused-promises`            | React 事件属性上直接传 async 函数（`onClick={copy}`）    |
| `require-await`                  | `async` 关键字白挂（处理器里根本没有 `await`）           |
| `no-base-to-string`              | `String(children)` 把 React 元素变成 `"[object Object]"` |
| `no-redundant-type-constituents` | `keyof Env & string` 里的 `& string` 是多余的            |

> ⚠️ **`recommendedTypeChecked` 里的 `no-unsafe-*` 一族要 `strict` 才准** ——
> 本项目的 tsconfig 全是 `strict: true`，所以 `any` 一律被报。
> ⚠️ **`require-await` 对 async generator 会误报** ——
> 它只在「`yield await x`」时才放行 async generator，而**签名要求 `AsyncGenerator`
> 的事件流 fixture 天然只有 `yield`**。这类要在文件顶部写一句
> `/* eslint-disable @typescript-eslint/require-await -- 原因 */`，
> **不要把规则整个关掉**（`require-await` 在普通 async 函数上是有价值的）。

> ⚠️ **类型感知 lint 比语法 lint 慢** —— 要构建 TS Program。
> 实测：`yarn lint` ~3.6s（纯语法只要 ~0.9s）；
> `yarn run check` 因为 typecheck 与 lint 并行，合计 ~5s（串行要 ~7s）。
>
> ⚠️ **想更快只有两条路** ——
> ① 减少 project 数量（每份 Program 都要重新解析 lib 文件，见 §A.3）；
> ② `eslint --cache`（增量 ~0.55s），
> ⚠️ 但**类型感知规则下缓存会漏报** —— A 文件的类型变了、B 文件没变时，
> B 的结果会被缓存复用，新出现的 `no-floating-promises` 之类的错误就看不见了。
> **默认不开** —— 一个会静默漏报的闸比慢 4s 的闸更危险。
> 想要更快，可以只保留真正值钱的几条规则，不必整套 `recommendedTypeChecked`。

### A.8 测试分层与反馈回路 ★

> **本节是「让 agent 跑测试不慢」的工程契约。**
> 目标：**改完代码的默认验证动作在 15 秒内结束**，
> 而不是每次都跑全量、每次都输出几百行。

#### A.8.1 为什么「行业标准的自动化测试」在 agent 手里会很慢

| 层             | 慢的根因                                                     | 本项目的对策        |
| -------------- | ------------------------------------------------------------ | ------------------- |
| **配置**       | 全局关并行 · 超时 30 秒 · unit/integration 混装 · e2e 走 dev | 见 A.8.2            |
| **Agent 行为** | 默认跑全量；测试输出全量进 context                           | 见 A.8.4 契约 1/2/3 |
| **测试设计**   | 粒度大 · 真 I/O · fixture 不复用 → flaky → agent 反复重跑    | 见 A.8.3            |

> ⚠️ **最隐蔽也最致命的一条**：**几百行 stdout 会塞满 agent 的 context**，
> 之后每一轮对话都变慢 —— 「agent 跑测试很慢」的隐形大头，
> 比任何配置优化都重要。

#### A.8.2 四层反馈回路

| 层  | 名称   | 目标耗时  | 跑什么                                         | 隔离方式                       | 命令                    |
| --- | ------ | --------- | ---------------------------------------------- | ------------------------------ | ----------------------- |
| L0  | 静态闸 | **< 8s**  | typecheck + lint（含类型感知，见 A.4 / A.4.1） | 无需隔离                       | `yarn run check`        |
| L1  | 单元   | **< 10s** | 纯逻辑，零 I/O                                 | `isolate: false`（无状态）     | `yarn test:unit`        |
| L2  | 集成   | **< 60s** | 真 SQLite · 真 Koa · mock 模型                 | **每测试文件一个独立 DB 文件** | `yarn test:integration` |
| L3  | e2e    | **< 3m**  | 5~8 条主路径                                   | 独立 browser context           | `yarn test:e2e`         |

**L0 · 静态闸**

- ⚠️ **任何一次改动后第一道永远跑它** ——
  类型错误在这一层被抓住，**绝不该以「测试失败」的形式出现在 L1**
  （那是 agent 最容易浪费时间的地方：把类型错误当测试失败去 debug）

**L1 · 单元**

- 断言的是**纯逻辑**：状态 reducer · 工具策略判定 · 占位符替换 ·
  沙箱路径判定 · FTS5 查询构造 · 命令黑名单匹配 · 成本计算
- `pool: 'threads'` + `isolate: false` —— 纯函数无状态，不需要重建模块上下文

**L2 · 集成**

- ⚠️ **每个测试文件用独立的 SQLite 临时文件**（`os.tmpdir()` + `mkdtemp`）
  —— **这是能开并行的前提**
  - ⚠️ **不要用「全局关并行」解决「共享 DB 互相干扰」** ——
    那是用全局代价换局部问题，正确解法是每文件隔离
- 真 Koa app（`supertest` 打 app 实例，**不起真端口**）
- ⚠️ **模型一律 mock**（一次真实调用就是钱）
- fixture：建一次模板库 → 每个测试**复制文件**（不是重建）

**L3 · e2e**

- ⚠️ **只测 5~8 条主路径** —— 细粒度断言属于 L1/L2 的活
- ⚠️ **不要用 `yarn dev` 起服务** ——
  它会起 Vite HMR + 跑迁移，冷启动 30~120 秒；改用 `vite preview` 吃预构建产物

#### A.8.3 测试设计约定

| 约定                                         | 理由                                                                                                             |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **测试文件 ↔ 源文件一一对应**                | `src/tools/builtin/read-file.ts` ↔ `tests/unit/tools/read-file.test.ts`                                          |
|                                              | ⚠️ **agent 能「猜」出该跑哪个测试文件**；反例是一个大而全的 `integration.test.ts` 跑整个系统 —— agent 只能全量跑 |
| **先写会失败的测试（red），再实现（green）** | 不只是 TDD：它让 agent 的下一步天然是「跑那一个测试」，反馈回路秒级                                              |
| **测试名写「行为」不写「实现」**             | agent 读测试名就知道期望是什么，不用读代码                                                                       |
| **重试只兜偶发失败**                         | `retries: 1`，但**重试仍失败必须标记为 flaky** —— 不许用重试掩盖真 bug                                           |
| **失败信息要能独立读懂**                     | agent 读不到源码上下文，错误信息必须自包含（期望值 + 实际值 + 出处）                                             |

#### A.8.4 给 Agent 的三个契约 ⚠️

> 这三条是**行为约束**，不是配置 —— 写在 [AGENTS.md §4.1](../AGENTS.md) 里同样生效。

**契约 1 · 反馈闸**

> 每次改完代码的**默认验证动作** = `yarn run check && yarn test:unit`（< 20 秒）。
> ⚠️ **禁止默认跑全量。** 全量只在「准备交付这条需求」时跑。
> ⚠️ **`yarn run check` = typecheck 与 lint 并行**（`concurrently -n tsc,lint -r`）——
> 实测 ~5s（串行 ~7s），仍在 20s 预算内。
> lint 曾经因 TS 7 兼容性问题跑不起来，已在 A.4 修好（TS 6 API + TS 7 编译器并存）。
> ⚠️ **写 `yarn run check`，别写 `yarn check`** —— yarn 1 自带同名内置命令
> （依赖树完整性检查），会盖过 package.json 里的脚本，报的是无关的依赖错误。

**契约 2 · 增量选测**

> 优先 `yarn test:related <改动的文件>`（Vite 模块图反查受影响测试），
> 拿不到 affected 时才退到 `yarn test:changed`（基于 git diff）。
> ⚠️ **别跑 `--changed` 当默认** —— 它依赖工作区干净，改动没提交时结果不准。

**契约 3 · 输出瘦身**

> 测试输出必须走 `agent` reporter（配置里已设）——
> **成功的用例一行都不打**，只有失败的才输出详情。
> ⚠️ **不要为了「看清楚」而加 `--reporter=verbose`** —— 那会把成功用例也打出来，
> 几百行进 context，后面每一轮都变慢。

#### A.8.5 加速手段清单（按性价比排序）

| 手段                               | 收益                          | 成本 |
| ---------------------------------- | ----------------------------- | ---- |
| **`agent` reporter**               | context 不爆炸 → 后续轮次都快 | 0    |
| **`--related` 增量选测**           | 全量 → 只跑受影响的           | 0    |
| **unit / integration 拆 projects** | 跑单测不加载集成测试文件      | 0    |
| **每 worker 独立 DB → 打开并行**   | 串行 → 并行（× 核数）         | 中   |
| **收紧超时**（unit 5s / int 15s）  | 失败时不等 30 秒              | 0    |
| **e2e 不走 `yarn dev`**            | 省 30~120 秒冷启动            | 中   |
| **fixture 复制而非重建**           | 每个测试省几百毫秒            | 小   |
| **`retries: 1` + flaky 标记**      | 减少偶发失败导致的反复重跑    | 小   |
| **别清 `node_modules/.vite`**      | 省 5~20 秒依赖预构建          | 0    |

#### A.8.6 实测基线（本机 M 系列 macOS）

| 动作                         | 耗时      | 备注                               |
| ---------------------------- | --------- | ---------------------------------- |
| `yarn test:unit`（3 个用例） | **1.1s**  | 含 yarn 启动开销；vitest 本体 61ms |
| `yarn test`（2 个 project）  | **0.5s**  | 并行                               |
| `yarn test:related <file>`   | **0.46s** | 「Affected 1 of 3 test files」     |

> ⚠️ **基线会随用例数增长** —— 上面是空库时的数字。
> 真实项目里 L1 应该在 **10 秒内**、L2 在 **60 秒内**、L3 在 **3 分钟内**。
> 超了就是测试设计有问题（见 A.8.3）。

#### A.8.7 Vitest 5 的两个坑

> ⚠️ **选项层级**：顶层选项挪进 `test:` **不报错，只会悄悄不生效**。
> `pool` / `fileParallelism` / `maxWorkers` 都得放对层 —— 改配置前先确认。
>
> ⚠️ **inline projects 共享 Vite server 与 transform cache**（Vitest 5 的优化）——
> 所以 `unit` / `integration` **写在同一个 `vitest.config.ts` 里**，
> 不要拆成两个独立配置文件（那会各起一个 Vite，缓存不共享）。

### A.9 环境变量校验（启动时挂）

- 所有环境变量走 **zod schema**（`src/config.ts` 里的 `envSchema`）
- **启动时校验，失败直接退出并打印缺哪个 key**
- ⚠️ **`.env` 和 `.env.example` 是同一份东西的两副面孔**：同一组 key、同一顺序、同一段注释，
  **只有值不同**（`.env` 写真值 / `.env.example` 留空）
- 「哪个 key 该存在」的唯一依据 = `envSchema`
- 改了 `envSchema` 必须同步两个文件，并跑 `yarn env:check`（漂了退出码 1）
- 兜底测试 `tests/unit/env-consistency.test.ts` 守着同一套不变量

**本项目的 key 分组**（详见 [11](./11-部署运维与成本.md)）：

| 组   | 典型 key                                                                          |
| ---- | --------------------------------------------------------------------------------- |
| 服务 | `PORT` / `NODE_ENV` / `HOST`                                                      |
| 存储 | `DATABASE_PATH` / `WORKSPACE_ROOT`                                                |
| 模型 | `LLM_BASE_URL` · `LLM_API_KEY` · `LLM_MODEL` · `LLM_FALLBACK_*`                   |
| 通用 | `MAX_TOOL_STEPS` / `TOOL_TIMEOUT_MS` / `DEFAULT_TEMPERATURE` / `MEMORY_*`         |
| 成本 | `MONTHLY_TOKEN_BUDGET` / `COST_BUDGET_BLOCK` / `WARN_RATIO`                       |
| 安全 | `ALLOW_PRIVATE_EGRESS` / `SHELL_ENABLED` / `TOOL_CONFIRM_LEVEL`                   |
| 编排 | `MAX_TOOLS_PER_TURN` / `SUBAGENT_*` / `CRON_ENABLED` / `SKILL_AUTOCREATE_ENABLED` |
| 上下文 | `AGENTS_MAX_CHARS`（**注入系统提示词的 `AGENTS.md` 截断上限**）                    |
| 浏览器 | `BROWSER_ENABLED` / `BROWSER_ALLOWED_DOMAINS`                                    |
| 日志 | `LOG_LEVEL`                                                                       |

> 📌 **`.env` 是本项目唯一的配置入口**（共 51 个 key）——
> 模型、通用配置、MCP server 全在这里配；前端没有设置页。
> 提示词（`prompts/*.md`）与长期记忆（`data/memory/*.md`）是**内容**不是配置，
> 仍以文件形式存在 —— 它们是多行文本、天天要改，而且要进 git。

### A.9.1 `.env` 里的 JSON 值

- ⚠️ **`.env` 里全是标量** —— **没有 JSON、没有数组、没有供应商前缀**：
  ```dotenv
  LLM_BASE_URL=https://open.bigmodel.cn/api/anthropic
  LLM_API_KEY=sk-xxxx
  LLM_MODEL=glm-5.3
  ```
  ⚠️ **列表型配置（MCP server 列表）放文件**（`data/mcp.json`），
  `.env` 里只留一个路径（`MCP_CONFIG_PATH`）
- ⚠️ **`LLM_MODEL` 留空是合法的** —— 「还没配置模型」是**运行时**提示，不是启动失败
- ⚠️ **跨字段校验**（`src/config.ts` 的 `validateRelations`）：
  配了 `LLM_MODEL` 却缺 `LLM_BASE_URL` / `LLM_API_KEY` ·
  备用模型三项只给了一部分 → **启动失败**并指出缺哪个

### A.10 错误处理约定

- 业务错误 → 抛 `AppError`（带 `code` / `status` / `message`）
- **模型与工具能读懂的错误必须转成文本回灌给模型**，
  而不是让整轮 500 —— 用户看到的是「工具失败了，原因 X」，不是白屏
- gateway 层统一把错误映射成 `{ error: { code, message } }`
- ⚠️ **不要把栈信息返回给前端**（生产模式）

### A.13 测试约定

> 分层与速度契约见 [A.8](#a8-测试分层与反馈回路-)（**先读那节**）。

| 层              | 放哪                 | 特点                                                        | 目标耗时 |
| --------------- | -------------------- | ----------------------------------------------------------- | -------- |
| **unit**        | `tests/unit/`        | 纯函数，无 DB、无网络；零 I/O                               | < 10s    |
| **integration** | `tests/integration/` | 真 SQLite 临时库（**每文件独立**）；模型调用 mock（零费用） | < 60s    |
| **e2e**         | `tests/e2e/`         | Playwright，真浏览器；**只测 5~8 条主路径**                 | < 3m     |

**目录与命名约定**（⚠️ 为了让 agent 能「猜」出该跑哪个测试）：

```
src/tools/builtin/read-file.ts   ↔  tests/unit/tools/read-file.test.ts
src/services/memory.ts           ↔  tests/unit/services/memory.test.ts
src/services/memory.ts           ↔  tests/integration/services/memory.test.ts
```

- ⚠️ **不要写一个大而全的 `integration.test.ts` 跑整个系统** ——
  那样 agent 只能跑全量，反馈回路直接退化
- ⚠️ **集成测试绝不能真调 LLM**（一次调用就是钱）——
  `vi.mock` 掉模型与向量模块，测试断言的是**编排行为**，不是模型输出
- 每个集成测试文件**自己建自己的库**（独立临时文件），用完删掉；
  **不共享状态，也不连开发库**

**fixtures 放 `tests/fixtures/`**：

- `db.ts` —— 建模板库 + 复制成独立临时库的助手
- `llm.ts` —— 模型响应的固定 fixture（成功 / 失败 / 超预算 / 拒绝）
- ⚠️ **fixture 只建一次、复制 N 次** —— 每个测试重建环境是慢和 flaky 的双重来源

**flaky 处理**：

- `retries: 1` 只兜偶发失败
- ⚠️ **重试仍然失败 = 真 bug 或真 flaky，必须记录下来**（不能靠重试让它变绿）
- ⚠️ **禁止在测试里 `sleep` 等待异步** —— 用轮询等待条件成立，超时才失败
  （`sleep` 是 flaky 的头号来源，也是慢的次要来源）
