# 05-b · 数据模型 · 全文检索（FTS5）

> 检索一律走 **SQLite FTS5**，不用向量。
> ⚠️ **不与业务库共用同一个 SQLite 文件**（原因见 [03-b §B.8](./03-b-技术栈-后端栈.md)）——
> FTS5 虚表跟业务表在**同一个** `data/atlas.db` 里（它们要一起事务写）。

## 5.1 用它存什么

| 用途             | 虚表           | 说明                                                                   |
| ---------------- | -------------- | ---------------------------------------------------------------------- |
| **会话内容检索** | `messages_fts` | 跨会话搜索「我上次说过的那件事」（对齐 Hermes 的 FTS5 session search） |
| **记忆检索**     | `memory_fts`   | 从 `data/memory/*.md` 解析进来的记忆条目                               |
| **Skill 匹配**   | `skill_fts`    | `SKILL.md` 的 name + description + 正文摘要                            |

> ⚠️ **本期没有「文档 RAG」**：不上传文档、不做语料库检索。
> 将来要加 RAG，是**新增一张 `documents_fts` + chunk 表**，不是改现有三张。
>
> ⚠️ **没有 embedding 模型这一层** —— 这是本期最重要的简化：
> 少一个依赖、少一个故障点（embedding 服务挂了要降级）、
> 少一份「换模型 → 旧向量作废 → 全量重算」的运维负担。
> 代价是**召回从「语义相似」变成「关键词匹配」**。

## 5.2 表结构

```sql
-- 会话消息全文索引（与 messages 表同库同事务）
-- 📌 **只索引正文** —— 消息 id / 时间从 messages 表 JOIN 出来，
--    不在虚表里存第二份（少一份就少一处会不同步）
CREATE VIRTUAL TABLE IF NOT EXISTS messages_fts USING fts5(
  content,
  session_id UNINDEXED,
  tokenize = 'trigram'
);

-- 记忆条目全文索引（从 data/memory/*.md 解析进来）
CREATE VIRTUAL TABLE IF NOT EXISTS memory_fts USING fts5(
  name,
  body,
  file UNINDEXED,
  tokenize = 'trigram'
);

-- Skill 全文索引
-- ⚠️ **还没建** —— Skill 机制没做（[12-c C4](./12-c-需求-工具技能与扩展.md)）
CREATE VIRTUAL TABLE IF NOT EXISTS skill_fts USING fts5(
  name,
  description,
  body,
  tokenize = 'trigram'
);
```

> 📌 **消息索引用触发器同步**（`messages_fts_ai` / `_au` / `_ad`）——
> 触发器**就在同一个事务里**，比「应用层写两张表」更不容易漏
> （消息要走 `create` / `update` / `destroy` 好几条路径）。
> 虚表与消息表按 **`rowid`** 对齐 —— 触发器里写 `new.rowid`。

### ⚠️ 分词器：`trigram` 是硬要求

- SQLite FTS5 默认的 `unicode61` 分词器**不切中文** ——
  一整句中文会被当成**一个 token**，
  于是搜「跑一下测试」搜不到「我今天跑了一下单元测试」
- **`tokenize='trigram'`**（SQLite ≥ 3.34 内置，不需要编译原生扩展）
  - 把文本切成 3 字符的滑动窗口 → 中文子串匹配可用
  - ⚠️ **代价**：
    - 查询词 **必须 ≥ 3 字符**（更短的词直接返回空，要走降级路径）
    - 英文也是 3 字符滑窗 —— 能用，但索引更大、查询稍慢
- ⚠️ **Hermes 自己为 FTS5 编译过 `native/fts5_cjk/`** —— 说明这块有坑。
  Atlas 用 `trigram` 绕开编译，**但必须先写一个最小验证**：
  中文短句能被搜到，且英文单词不被拆坏

> ⚠️ **不要写死「相似度阈值」** —— 不同分词器 / 不同语料的基线差很多。
> 只做**相对排序**取 top N。

## 5.3 写入

| 事件               | FTS5 动作                       | 真源动作                    |
| ------------------ | ------------------------------- | --------------------------- |
| 消息写入           | **触发器** insert `messages_fts`（同事务） | insert `messages` |
| 消息改 / 删        | **触发器** 重建该行             | update / delete `messages`  |
| 记忆文件变更       | **全量重建** `memory_fts`       | 写 `data/memory/*.md`       |
| Skill 装 / 卸 / 改 | 重建对应条目                    | 改 `data/skills/*/SKILL.md` |

- ⚠️ **消息索引必须与消息写入在同一个事务里** ——
  分两次写会出现「消息在但搜不到」或反之；
  **触发器天然满足这一点**
- ⚠️ **记忆与 Skill 是「全量重建」不是「增量 upsert」**：
  它们的真源是 Markdown 文件，增量同步的 bug 面比全量重建大得多
  （量级小：记忆 ≤ 50 条，Skill 个位数，全量重建是毫秒级）
- ⚠️ **重建的触发时机**：启动时全量重建一次 + 文件 mtime 变化时重建
  （不靠 watcher，用「每次读记忆时比对 mtime」这种懒检测就够了）

## 5.4 检索

```
search(query, tables[], topK)
  → 每个虚表 FTS5 查一次（BM25 排序）
  → 合并各表结果
  → 取 topK
  → ⚠️ 交给 LLM 摘要成一段（不是把原文全塞进上下文）
```

- ⚠️ **命中内容必须先摘要再进上下文**（对齐 Hermes「FTS5 检索 + LLM 摘要」）
  —— 命中 5 条长消息会直接撑爆预算
- ⚠️ **查询词 < 3 字符**：trigram 匹配不到 → **不查**（返回空）
- ⚠️ **不要在 SQL 里拼用户输入的查询串** → 用 FTS5 的参数化查询
  （`MATCH :match`），避免引号 / 运算符导致的语法错
- ⚠️ **查询词要包成短语**（`"关键词"`）—— 用户输入里的 `-` `*` `:`
  会把 FTS5 的查询语法搞坏；引号本身要转义（`"` → `""`）
  （实现见 `src/lib/fts.ts` 的 `toMatchQuery()`）

## 5.5 降级策略 ⚠️

FTS5 是 SQLite 的**编译期可选特性** —— 某些发行版的 SQLite 没编进去。

| 情况            | 行为                                                       |
| --------------- | ---------------------------------------------------------- |
| 没有 FTS5       | **服务照常启动**；检索降级为「按时间倒序取最近 N 条」      |
| 没有 FTS5       | 记忆召回降级为「按时间倒序」；Skill 匹配退化为「全量注入」 |
| trigram 不可用  | 退回 `unicode61` + 明确提示「中文检索效果下降」            |
| 查询词 < 3 字符 | 该次查询降级为「时间倒序」，不报错                         |

> ⚠️ **降级不能让服务起不来**。检索是增强能力，不是必需件。
> ⚠️ **启动时探测**：**建一张临时虚表再删掉** ——
> 探测要**真建表**，只查 `compile_options` 会漏掉
> 「编了但版本太老没有 trigram」的情况（`src/lib/fts.ts` 的 `probeFts()`）。
> ⚠️ **退到 `unicode61` 也要明确提示**「中文检索效果下降」。

## 5.6 与真源的同步关系

| 事件              | FTS5 动作                           | 真源动作                    |
| ----------------- | ----------------------------------- | --------------------------- |
| 记忆新增 / 改写   | 重建 `memory_fts`                   | 改 `data/memory/*.md`       |
| 记忆归档（软删）  | 重建（条目标 archived，**不注入**） | 条目加 `status: archived`   |
| 记忆物理删除      | 重建（条目移除）                    | 从文件里删掉该小节          |
| Skill 安装 / 更新 | 重建 `skill_fts`                    | 改 `data/skills/*/SKILL.md` |
| Skill 卸载        | 重建（条目移除）                    | 删目录                      |

> ⚠️ **「先写真源再重建索引」**：索引重建失败不回滚文件（文件是权威副本），
> 失败记 warn 并标记「待重建」，下一轮启动时补上。
> 📌 **命令行**：`yarn search <关键词>` —— 直接看命中（跨会话 + 记忆）。
> ⚠️ **文件写入本身要原子**（临时文件 + `rename`）——
> 文件写一半被 kill，记忆就真丢了。

## 5.7 备份

- **只有一个数据文件**：`data/atlas.db`（含业务表 + FTS5 虚表）
  —— 不像以前还要单独对 `vectors.db`
- 备份脚本：`scripts/backup.ts`（`yarn backup`）
  - SQLite 在线备份用 `VACUUM INTO`（不要直接拷文件 —— WAL 模式下拷文件可能拿到不一致的快照）
- ⚠️ **记忆文件也要备份**：`data/memory/*.md` 与 `data/atlas.db` 一起备份
  （记忆的真源在文件里，索引丢了可以重建，**文件丢了就真丢了**）
- ⚠️ **恢复后要校验**：索引条数与真源条数对不上 → 重建索引

## 5.8 与「走向量」的对比（为什么本期不用）

| 维度     | FTS5（本期）            | 向量（sqlite-vec）    |
| -------- | ----------------------- | --------------------- |
| 依赖     | SQLite 内置，零额外依赖 | 原生扩展，可能装不上  |
| 召回     | **关键词匹配**（子串）  | 语义相似              |
| 中文     | `trigram` 可用          | 取决于 embedding 模型 |
| 换模型   | **无影响**              | 维度变了要全量重算    |
| 故障降级 | 退回时间倒序            | 退回时间倒序          |
| 运维     | 无                      | 多一个文件要一起备份  |

> ⚠️ **什么时候该换成向量**：
>
> - 用户开始抱怨「换个说法就搜不到了」（同义 / 口语化表达）
> - 记忆条目涨到几百条以上，关键词命中开始变噪声
>
> 换的时候**只动 `src/services/search.ts` 里那一层读写** ——
> 这就是为什么检索操作要单独封一个模块，不要散在业务里。
> （Atlas 的 `services/memory.ts` 里已经有同样的「统一入口」约定，
> 对应 [12-e E3](./12-e-需求-观测安全与验收.md) 里「评测与线上走同一个 `planRetrieval()`」的要求。）
