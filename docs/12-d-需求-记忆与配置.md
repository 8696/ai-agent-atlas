# 12-d · 需求 · 记忆与配置（D 类需求）

> 编号接续 [12-c](./12-c-需求-工具技能与扩展.md)。
>
> 🎯 **记忆体系对齐 Hermes**：长期记忆是**两个 Markdown 文件**
> （`MEMORY.md` / `USER.md`），检索用 **SQLite FTS5 全文索引**，
> 不再依赖 embedding 模型 —— 少一个依赖、少一个故障点，且人能直接改。

## D1 · 短期记忆与会话状态 · P0 ✅

**需求**：Agent 记得这轮对话里说过什么，跨轮不丢上下文；会话太长时能压缩。

**技术要求**：

- **两层**：
  - **消息历史**（`messages` 表）：用户 / 助手 / 工具结果
  - **图状态**（`graph_checkpoints`）：LangGraph 的完整状态
- 两者都要有：消息历史用于「展示与统计」，图状态用于「继续跑」
- **长会话不能无限增长**：超出 token 预算时触发**摘要压缩**
  - 被裁掉的早期轮次调一次 LLM 折成摘要，写进 `sessions.summary`
  - `sessions.metadata.summary_boundary` 记「摘要覆盖到哪条消息为止」
  - 下一轮按边界把历史切成两段 —— **边界之前不再喂原文**
    （否则原文 + 摘要两种说法并存）
  - **滚动重写**：输入是「旧摘要 + 新丢掉的轮次」，输出是一份全新的完整摘要（不是追加）
- ⚠️ **手动压缩**（对齐 Hermes 的 `/compress`）：
  - 斜杠命令 `/compress` 触发**同一个压缩函数**（不是另一条代码路径）
  - 手动压缩**忽略 token 阈值**，立即把当前全部历史折成摘要
  - 压缩后用户仍能翻到完整历史（消息表没删，只是不再进模型上下文）
- ⚠️ **摘要用「干脏活的那个模型」**（**辅助模型优先**，见 [12-a A7](./12-a-需求-应用外壳与上下文.md)）
  → ⚠️ **摘要也是大模型调用 = 成本高**，所以摘要触发要保守（预算够才做）；
  配了辅助模型的话，摘要走便宜的那个
- 摘要**不另起记录** —— 花费直接记进 `cost_logs` 的 `usage_scope='summary'`，
  ⚠️ **没有单独的「对话记录」表** —— 耗时靠工具流水的 `duration_ms` 体现
- 摘要开关与预算在代码常量里（``.env` 的 `SUMMARY_ENABLED`` / ``.env` 的 `SUMMARY_TOKEN_BUDGET``，
  改完重启生效）
- ⚠️ **摘要是 fire-and-forget**：进程在写完前被 kill，这段摘要就丢了（下一轮重来）；
  重复摘要只是多花一次钱，不会写坏数据（写之前会重读边界）

**验收**：

- [x] 多轮对话里，Agent 能引用前面说过的信息
      （**真模型实测**（智谱 GLM）：先让它列工作区文件，再问
      「我刚才让你看的那个目录里，有个文件叫「验证文件.txt」吗？」——
      **零工具调用**就答对了，还知道是在工作区根目录）
- [x] 长会话触发摘要后，早期内容不再以原文形式出现在上下文里
      （`prepareSessionContext()`：**边界之前只剩摘要**，原文一条都不再喂）
- [x] `/compress` 手动触发 → 上下文被折成摘要，且历史消息仍可在界面上翻到
      （斜杠命令 → **同一个压缩函数**；`messages` 表不删，只是不再进模型上下文）
- [x] 摘要开关关掉后，超长会话走「截断」而不是「摘要」
      （`SUMMARY_ENABLED=false` → `truncateOldest()`：**丢最旧的，留最后一条用户消息**）
- [x] 摘要调用单独记一条，不混进对话记录
      （⚠️ 本期**没有调用链体系** —— 摘要**不另起记录**，
      花费记进 `cost_logs` 的 `usage_scope='summary'`）

>   每轮开头裁一次，工具循环里**不重复裁**
> - ✅ **边界存在 `sessions.metadata.summary_boundary`**（**消息 id**），
>   摘要正文在 `sessions.summary`

## D2 · 长期记忆（Markdown 文件） · P1 ✅

**需求**：Agent 能记住「关于这个用户的事实」，跨会话生效。
记忆存在**人能直接读懂、能直接改的 Markdown 文件**里（对齐 Hermes）。

**技术要求**：

- **两个文件**（对齐 Hermes 的 `MEMORY.md` / `USER.md`）——
  分别是 [12-a A4](./12-a-需求-应用外壳与上下文.md) 分层里的 **L2 语义记忆**与 **L3 用户画像**：

  | 文件                    | 装什么                                                 |
  | ----------------------- | ------------------------------------------------------ |
  | `data/memory/MEMORY.md` | Agent 侧的记忆：环境事实、做过什么、踩过的坑、任务套路 |
  | `data/memory/USER.md`   | 用户侧的记忆：偏好、身份、习惯、工作方式               |

- ⚠️ **启动时自动创建**（**空文件** —— 文件里只装条目，**不带默认头注**）
  —— `data/` 不进 git，新机器上这两个文件本来就不存在
  - 📌 **为什么不要出厂头注**（2026-11-01 改）：
    ① **头注会误导人** —— 那段「条目格式」示例长得跟真条目一样，
    人（和模型）打开文件会以为那是一条记忆；
    ② **头注占预算** —— `USER.md` 上限只有 1375 字符，
    一段 500 字符的样板说明直接吃掉三分之一
  - 📌 **格式说明在别处** —— 本文档的「条目格式」一节 +
    `memory` 工具的参数 schema；**用户自己写的头注一律保留**
- **条目格式**（每个 `##` 小节 = 一条记忆，YAML frontmatter + 正文）：

  ```markdown
  ## prefers-pnpm

  - kind: preference # preference | fact | context | profile
  - confidence: 0.9
  - source: auto # auto | manual
  - updated: 2026-10-31

  用户用 pnpm，不用 npm（装依赖、跑脚本都是）。
  ```

  - ⚠️ **不要用自由格式散文** —— 结构化条目才能被 FTS5 索引、才能被程序增删改
  - 正文保持**一句话能说完**；太长就拆成多条

- ⚠️ **每个文件有字符上限**（对齐 Hermes）：
  | 文件        | 上限          | env key            |
  | ----------- | ------------- | ------------------ |
  | `MEMORY.md` | **2200 字符** | `MEMORY_MAX_CHARS` |
  | `USER.md`   | **1375 字符** | `USER_MAX_CHARS`   |
  - **超限不自动压缩**，只**报告**「已满，需要你整合一下」
    （Hermes 也不自动压缩 —— 自动压缩会悄悄丢用户的记忆）
  - ⚠️ **上限也是「防重复追加」的机制** —— 文件满了就逼着改写而不是继续堆
- **三级更新机制**：
  1. **T1 正则信号预筛**（零成本）：对话里出现「记住 / 我喜欢 / 我叫 / 我用 …」
     这类信号才触发抽取 —— 挡住大部分对话
  2. **T2 调 LLM 抽取**：把现有记忆（相关部分 + 摘要）一起喂给模型，
     模型决定**新增 / 改写 / 归档**
     （⚠️ **走辅助模型优先** —— 见 [12-a A7](./12-a-需求-应用外壳与上下文.md)）
     ⚠️ **提示词里要写死「已有则改写，不要重复追加」** ——
     模型看得见已有条目，不需要额外做字符串匹配
  3. **T3 用户手动改**：**直接编辑文件** 或用命令行
     （`yarn memory:list` / `add` / `edit` / `archive` / `delete` / `clear`）
- **注入走 system prompt**，且排在检索资料段**前面**
  - ⚠️ **注入时带上用量表头**（如「记忆库已用 67%，1474 / 2200 字符」）——
    让模型**知道自己记了多少、还剩多少**，否则它会以为记忆是无限的
    （对齐 Hermes 的用量表头）
    ⚠️ 冲突时以工具返回的事实为准（记忆是「偏好」，不是「世界事实」）
- **注入哪几条按「与当前问题相不相关」排**（不是固定顺序）：
  - **相关性是主序**，优先级（来源 > 置信度 > 更新时间）是兜底
  - ⚠️ **没有索引的记忆按 0 分算**（跟「有索引但不相关」同档）——
    不会被「缺索引」饿死
- **每轮 top N 条 + token 预算双重裁剪**
- ⚠️ **写入时的并发安全**（Markdown 没有事务）：
  - 抽取是 fire-and-forget，可能和用户手动编辑撞车
  - 写入流程必须是「**重读 → 合并 → 原子写**」
    （写临时文件 + `rename`），不能直接原地覆盖
  - ⚠️ **原子写失败不能留半个文件** —— 记忆文件损坏 = 用户全部记忆丢失
- **归档**：条目 `status: archived`（软删：不再被召回，但文件里还看得见）
- ⚠️ **永久删除 = 真的从文件里移除**（用户行使「删除我的全部个人数据」的权利时要的是真删）
- 删除写审计（`MEMORY_DELETED`）
- ⚠️ **向量不再需要** —— 检索改走 FTS5（见 D3），`memories` 表删除，
  `embedding` / `embedding_model` 字段一起消失

**验收**：

- [x] 说「记住我 prefers pnpm」→ 下一轮回答里体现用了这个偏好
      （**三段都有测试守着**：

      （`writeMemoryEntries()`：**超限直接不写**，回一句「已满，需要你整合一下」）

## D3 · 跨会话检索（FTS5） · P1 ✅

**需求**：Agent 能翻出「我上次说过的那件事」——
跨会话搜索历史对话 + 记忆，并自动把命中内容摘要成一段。

**技术要求**：

- ⚠️ **检索口径**：两处都走 FTS5
  - **会话内容**（`messages` 表）→ FTS5 虚表 `messages_fts`
  - **记忆文件**（`MEMORY.md` / `USER.md`）→ FTS5 虚表 `memory_fts`
- ⚠️ **中文分词是硬骨头**：
  - SQLite FTS5 默认 `unicode61` 分词器**不切中文**，
    一整句中文会被当成一个 token → 搜「跑一下测试」搜不到「我今天跑了一下单元测试」
  - **方案：用 `tokenize='trigram'`**（SQLite ≥ 3.34 内置，不需要额外编译）
    - 代价：查询词 **≥ 3 字符**；英文按 3 字符滑窗匹配（能用但慢）
  - ⚠️ **Hermes 自己为 FTS5 编译过 `native/fts5_cjk/`** —— 说明这块有坑，
    实现时先写一个最小验证：中文短句能被搜到
  - ⚠️ **降级路径**：启动时探测 FTS5 + trigram 是否可用
    （`SELECT ... FROM pragma_compile_options()`）——
    **不可用就退回「时间倒序取最近 N 条」**，功能少一半但**不影响对话**
- **检索流程**：
  1. 用用户当前问题做 FTS5 查询（`messages_fts` + `memory_fts`）
  2. 取 top K 条命中（默认各 5 条）
  3. ⚠️ **命中内容交给 LLM 摘要成一段**（不是全量塞进上下文）——
     这是 Hermes「FTS5 检索 + LLM 摘要」的标准做法
     （⚠️ **走辅助模型优先** —— 见 [12-a A7](./12-a-需求-应用外壳与上下文.md)）
  4. 摘要作为「历史检索结果」段注入上下文
- ⚠️ **跨会话检索不另起记录** —— 花费记进 `cost_logs` 的 `usage_scope='retrieval'`
- **CLI 工具**：`yarn search:<关键词>`（跨会话 + 记忆搜索，直接看命中）

**验收**：

- [x] 问「我上次是怎么配那个数据库的」→ 能命中几周前的对话内容
      （⚠️ **这条本来是坏的** —— 查询被整句包成短语，
      自然语言问题在历史消息里**根本不是连续子串**，永远命中不了；
      **已修**：`toMatchQuery()` 现在**拆词**（中文 3 字滑窗 · 英文按词去停用词），

## D5 · 对话内记忆管理 · P1 ✅

**需求**：用户在对话里就能增删改自己的长期记忆 ——
「记住我用 pnpm」「把那条关于生日的记忆删掉」「以后别记我的地址」「清空我的记忆」，
**说完就生效**，不用去翻 `data/memory/*.md` 或敲命令行。

⚠️ **这条补的是 D2 的一个洞** —— D2 把记忆的读写做全了
（`yarn memory:*` 命令行 + 直接编辑文件），
但**对话里没有入口**：Agent 既没有工具，也没人告诉它记忆文件在哪。
用户说「删掉那条记忆」，它只能**口头答应**（实际什么都没做）——
记忆的信任问题比功能缺失更严重。

**技术要求**：

- **两个内置工具**（清单见 [12-c C2](./12-c-需求-工具技能与扩展.md)）：

  | 工具            | 动作                          | 敏感档   | 说明                                          |
  | --------------- | ----------------------------- | -------- | --------------------------------------------- |
  | `memory`        | `list` / `add` / `edit` / `archive` | normal   | **不弹确认** —— 条目还在文件里，可恢复       |
  | `memory_forget` | `delete` / `clear`            | **high** | **弹确认卡片** —— 永久删除不可恢复           |

  ⚠️ **为什么拆成两个工具** —— 敏感档是**按工具**定的、不是按参数定的
  （见 [12-c C3](./12-c-需求-工具技能与扩展.md)）：
  一个工具没法做到「新增不确认、删除要确认」。
- 📌 **走现成的服务层接口**（`services/memory/index.ts`）——
  工具不自己拼文件路径；写前扫描 / 原子写 / 删除审计 / 索引重建全都复用
- ⚠️ **子代理不能调**（`executor: 'none'`）——
  记忆是跟用户直接对话的事，子代理静默改写用户画像不合适
- **提示词里要有「记忆管理」这一节**（`prompts/tool.md`）——
  否则模型不知道有这两个工具，也不知道条目名要 kebab-case
- ⚠️ **同一轮不能写两遍** —— 主代理用工具写完，
  这一轮结束后的**自动抽取**要跳过（否则同一条记忆写两条、名字还不一样）
  —— `services/memory/manual-write.ts` 记一笔，**窗口 60 秒**
- **T1 闸要认「管理意图」** —— 「删掉关于我生日的记忆」不含任何可记的事实，
  原来的信号一个都不命中 → 抽取压根不启动 →
  `MEMORY_MANAGEMENT_SIGNALS` 单独一组
  ⚠️ **必须跟「记忆」沾边** —— 「把这个文件删掉」不能命中（白花一次模型调用）
- **斜杠命令 `/memory`** —— `list` / `delete <file> <名字>` / `clear <file>`，
  **零 LLM 调用**（跟其它斜杠命令一样）

**验收**：

- [x] 说「记住 X」→ 主代理调 `memory` 工具 → 条目落进 `data/memory/USER.md`
- [x] 说「把那条记忆删掉」→ 调 `memory_forget` → **弹确认卡片** →
      批准后文件里真没了（`deleteMemoryEntry()`）
- [x] 说「别记了那条」→ `memory` 的 `archive` → 不再被召回，**文件里还看得见**
- [x] 同一轮里工具写过一次 → 自动抽取**不再写第二遍**

- [x] `/memory` 列出全部条目（**带用量表头**）· `/memory clear USER` 清空一个文件
- [x] ⚠️ 条目名不合法 / 缺参数 / 记忆不存在 → **明确报错，不装成功**

## D6 · 单轮 token 上限 · P1 ✅

**需求**：一轮里累计用掉的 token 超过上限就**收尾** —— 别让某一轮无限烧下去。

⚠️ **它跟月度预算不是一回事** ——
月度预算（[D4](#d4--预算与成本控制--p1-)）是「这个月一共花多少」，
**粒度太粗**：一轮跑飞了，要等月底才看得出来。
单轮上限是**第二道刹车**，粒度是「这一轮」。

**技术要求**：

- `.env` 的 `MAX_TOKENS_PER_TURN`（**默认 0 = 不限**）——
  ⚠️ **默认不限**：不擅自加限制；想要「一轮别烧太多」就自己设一个数
- ⚠️ **判的是「本轮」** —— 图状态里另有一个 `turn_tokens` 通道，
  **每轮开头（`prepare`）清零**，跟跨轮累计的 `budget_used` 是两回事
- 超过上限 → **路由直接进 `answer`**（不再继续调工具），
  并发一条 `data-notice` 说清「已达上限」
  （⚠️ **要说清为什么停** —— 用户要知道是上限而不是「它不想干了」）
- ⚠️ **上限是 0 时这条逻辑整个不生效** —— 别给正常对话添限制

**验收**：

- [x] `MAX_TOKENS_PER_TURN=0`（默认）→ 行为与之前完全一致（不限）
- [x] 设了上限 → 这一轮累计超了就进 `answer`，并给出提示
- [x] ⚠️ 提示里说清「改 `.env` 的 `MAX_TOKENS_PER_TURN` 可以调」
