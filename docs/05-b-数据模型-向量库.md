# 05-b · 数据模型 · 向量库

> 本地向量库：**sqlite-vec**（原生扩展），独立文件 `data/vectors.db`。
> ⚠️ **不与业务库共用同一个 SQLite 文件**（原因见 [03-b §B.8](./03-b-技术栈-后端栈.md)）。

## 5.1 用它存什么

| 用途             | `kind`    | 说明                                                  |
| ---------------- | --------- | ----------------------------------------------------- |
| **长期记忆向量** | `memory`  | 每条记忆一条向量，用于「按与当前问题的相关性召回」    |
| **Skill 索引**   | `skill`   | 技能描述的向量，用于「这句话像不像某个技能的适用场景」 |

> ⚠️ **本期没有「文档 RAG」**：不上传文档、不做语料库检索。
> 向量库只服务于记忆召回与 Skill 匹配。
> 将来要加 RAG，是**新增一个 `kind='document'` + 新的 chunk 表**，不是改现有两张。

## 5.2 表结构

```sql
CREATE TABLE IF NOT EXISTS vec_items (
  id         TEXT PRIMARY KEY,
  kind       TEXT NOT NULL,          -- 'memory' | 'skill' | 'document'
  ref_id     TEXT NOT NULL,          -- 业务库里的主键（memories.id / skills.name）
  text       TEXT NOT NULL,          -- 原文（可读，便于人工核对）
  embedding  BLOB NOT NULL,          -- 归一化后的 float32 数组
  dim        INTEGER NOT NULL,       -- 向量维度
  model      TEXT NOT NULL,          -- 生成它的 embedding 模型名
  metadata   TEXT,                   -- JSON：额外字段
  created_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_vec_items_kind ON vec_items (kind);
CREATE UNIQUE INDEX IF NOT EXISTS idx_vec_items_ref ON vec_items (kind, ref_id);
```

### 向量表（sqlite-vec 的虚拟表）

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS vec_items_v USING vec0(
  embedding float[768] distance_metric=cosine
);
```

> ⚠️ **维度必须固定**：sqlite-vec 的虚拟表**建表时就定死维度**。
> 换 embedding 模型（维度不同）= **重建虚拟表**。
> 业务表 `vec_items.dim` 记录了每条向量的维度，
> 启动时对比「表里现存的维度」与「当前模型维度」，不一致就重建并重算。

## 5.3 写入

```
upsert(kind, refId, text, embedding, model)
  → 业务表 upsert（items）
  → 虚拟表 upsert（items_v）
```

- ⚠️ **两边必须一起写**：只写一边会出现「业务表有记录但搜不到」
  或「搜到了但业务表查不到」
- 写入前**归一化**（L2）→ 用余弦相似度时归一化后余弦 ≈ 点积
- 删除：`kind + ref_id` 定位后两边一起删

## 5.4 检索

```
query(kind, queryEmbedding, topK, filter?)
  → vec_items_v 按余弦距离取 topK
  → 用 ref_id 回业务表取完整记录
  → （可选）按业务字段二次过滤（如只取 status='active' 的记忆）
```

> ⚠️ **二次过滤在向量库这层做不了**（sqlite-vec 不支持任意 where）。
> 做法是：向量库取 `topK * 3` 条，回业务表过滤后再截断到 `topK`。
> ⚠️ **过滤掉的比例高时会不够 `topK`** —— 这时要**放宽重取**，不能直接返回不足的结果。

## 5.5 降级策略 ⚠️

sqlite-vec 是**原生扩展**，可能装不上（编译失败 / 平台不支持）。

| 情况             | 行为                                                       |
| ---------------- | ---------------------------------------------------------- |
| 扩展加载失败     | **服务照常启动**；向量检索降级为「进程内线性扫描」         |
| 扩展加载失败     | 记忆召回降级为「按时间倒序取前 N 条」（跟「没有相关性排序」一样） |
| 虚拟表维度不匹配 | 重建虚拟表 + 重算向量（或标记「需要重算」）                |

> ⚠️ **降级不能让服务起不来**。向量是增强能力，不是必需件。

## 5.6 与业务库的同步关系

| 事件             | 向量库动作           | 业务库动作             |
| ---------------- | -------------------- | ---------------------- |
| 记忆创建 / 改写  | upsert 向量          | upsert `memories`      |
| 记忆归档（软删） | **删向量**            | `status='archived'`    |
| 记忆物理删除     | 删向量                | 删行                   |
| Skill 安装 / 更新 | upsert 向量          | upsert `skills`        |
| Skill 卸载       | 删向量                | 删行                   |
| 换 embedding 模型 | **全部重建**         | 标记 `embedding_model` 不匹配 → 后台重算 |

> ⚠️ **「先写业务库再写向量」**：向量写失败不回滚业务库（业务库是权威副本），
> 失败记 warn 并把该行标记为「待补算」，下一轮后台补算。

## 5.7 备份

- `data/vectors.db` 与 `data/atlas.db` **一起备份**（两者要对得上）
- 备份脚本：`scripts/backup.ts`（`yarn backup`）
  - SQLite 在线备份用 `VACUUM INTO`（不要直接拷文件 —— WAL 模式下拷文件可能拿到不一致的快照）
- ⚠️ **恢复后要校验**：向量条数与业务表条数对不上时，提示「需要重算」

## 5.8 与「放 Qdrant」的对比（为什么本地）

| 维度       | sqlite-vec（本期）        | Qdrant              |
| ---------- | ------------------------- | ------------------- |
| 部署       | 零依赖，进程内             | 要起容器 / 远程服务   |
| 备份       | 拷文件                    | 要单独备份           |
| 过滤       | 只能 `kind` + 二次过滤    | 完整 payload 过滤    |
| 规模       | 万级以内够用              | 百万级               |
| ⚠️ 代价    | 维度写死在建表时           | 多一个基础设施       |

> ⚠️ **换 Qdrant 时要动的只有 `src/services/memory-relevance.ts` 里那一层向量读写** ——
> 这就是为什么向量操作要单独封一个模块，不要散在业务里。
