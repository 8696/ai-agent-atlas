# 08 · 评测方案

> 目标：**能回答「我改了提示词 / 换了模型，到底是变好了还是变差了」**。
> 需求侧见 [12-e E3](./12-e-需求-观测安全与验收.md)，模块侧见 [07-e 模块 15](./07-e-模块-可观测与评测.md)。

## 8.1 评测集

- 格式：**JSONL**，一题一行
- 每题字段：

  | 字段            | 必填 | 说明                                        |
  | --------------- | ---- | ------------------------------------------- |
  | `id`            | 是   | 稳定标识（A/B 配对靠它）                    |
  | `question`      | 是   | 用户问题                                    |
  | `expectations`  | 否   | 期望要点（数组），裁判据此打分              |
  | `tags`          | 否   | 分组标签（用于分组统计）                    |
  | `tools_allowed` | 否   | 允许使用的工具白名单（不给就用全局池）      |

- 示例：

  ```jsonl
  {"id":"q1","question":"工作区里有哪些文件？","expectations":["调用了 list_dir","列出了至少一个文件"],"tags":["tools"]}
  {"id":"q2","question":"记住我 prefers pnpm","expectations":["确认已记住该偏好"],"tags":["memory"]}
  ```

- 导入：后台上传 `.jsonl`；重复 `id` 覆盖；导入结果返回「新增 / 更新 / 跳过」计数
- 题量上限：单集 500 题（⚠️ 单次跑批上限是 50 题 —— 分批跑）

## 8.2 跑批

- **后台异步**：创建 run 立刻返 202 + `run_id`
- **单次最多 50 题**（`EVALUATION_MAX_ITEMS`）—— 成本闸门，一题 = 2 次 LLM 调用
- 跑批过程中每题独立记一条结果，**中途失败不影响其他题**
- `run_trigger`：`manual`（手动）/ `prompt_regression`（提示词发布自动触发）
  ⚠️ **列名不能叫 `trigger`**（是部分数据库的保留字；SQLite 不报错但迁库会炸）
- 每条结果记：题目 · 模型回答 · 四维分数 · 总分 · token · 费用 · 耗时 · 错误

## 8.3 裁判（LLM-as-Judge）

| 维度       | 打分范围 | 含义                                   |
| ---------- | -------- | -------------------------------------- |
| 准确性     | 1-5      | 有没有事实错误                           |
| 完整性     | 1-5      | 该说的要点有没有漏                       |
| 相关性     | 1-5      | 有没有答非所问                           |
| 格式       | 1-5      | 结构是否符合要求                         |
| **总分**   | 加权     | 上述四项的加权平均                       |

- 裁判用**固定模型**（不能跟被测模型同一个配置，否则换模型会换裁判）
- ⚠️ **裁判结果有随机性**：同一份回答两次打分可能差 0.5 分 ——
  所以对比要看**差值大于抖动阈值**才算「有区别」
- 裁判调不通 → 该题记为失败，不阻塞整批

## 8.4 口径一致性 ⚠️（最容易出错的地方）

```
线上对话 ──┐
           ├──→ planRetrieval()  ← 唯一入口
评测跑批 ──┘
```

- **检索 / 记忆召回 / 查询改写**这些「影响输入」的环节，
  线上和评测**必须走同一个函数**
- ⚠️ 不许评测里另写一套（哪怕「只是复现一下」）——
  线上开了某个开关、评测没开，**分数就不能代表线上表现**，
  「改坏提示词 → 分数跌 10%」这个基线直接歪掉
- **结构性守卫**：加一个测试断言「对话链路与评测链路调用的是同一个入口」

## 8.5 提示词改动自动回归

- 触发：**提示词发布 / 回滚**之后
- 范围：**前 10 题**（跑全集 = 100 次 LLM 调用，太贵）
- 异步，⚠️ **永不阻塞发布**：
  - 没评测集 → 跳过
  - 评测功能关闭 → 跳过
  - 起跑失败 → 跳过
  - ⚠️ **「发布后验证」不是「发布前门禁」** —— 新提示词已经生效才跑回归
- **显式传刚发布的版本号**，不依赖「当前生效指针」
  （发布与回归之间隔着一次 HTTP，中间可能又发了一版）

## 8.6 A/B 对比

- 入口：`GET /api/v1/admin/evaluation/compare?run_id_a=&run_id_b=`
- 输出：四维 + 总分的 A / B / 差值；token / 成本 / 题数差值；**逐题**谁更好谁更差
- 逐题配对（`matchComparisonItems`）：
  1. 按 `item_id` 精确配
  2. 配不上按题目文本兜底
  3. **一对一**（B 侧每条明细最多被领走一次）
- ⚠️ **路径是 `/evaluation/compare`，不是 `/evaluation/runs/compare`**
  —— 后者会被 `/evaluation/runs/:id` 那个动态路由抢先匹配掉
- 三种版本语义：
  - **不传** `prompt_version` → 跟随当前生效版本
  - 传 `null` → 显式用内置默认
  - 传版本号 → 用那一版；⚠️ **版本不存在直接 400，不静默回落默认**

## 8.7 已知边界

- ⚠️ **一次 A/B = 两跑批 = 成本翻倍**（50 题两批 = 200 次 LLM 调用）
  → 省钱的做法是用小评测集（1~5 题）
- ⚠️ **逐题明细上限 2000 条**（超了截断并在提醒条里说明）
- ⚠️ **不是流量分流的 A/B** —— 是离线对比，没有「按流量分版本」那回事
- ⚠️ **差异不保证只来自提示词**（模型不同 / 记忆变了 / 题目顺序影响生成）
  → 页面的提醒条要点出「模型不同」「同一个版本」这两种最常见的情况
- ❌ 不做定时自动跑全量
- ❌ 不做人工标注（没有标注界面）
