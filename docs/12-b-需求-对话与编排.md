## B1 · 流式对话 · P0

**需求**：用户在 `/chat` 发消息，Agent **逐字**流式返回，工具调用过程可见。

**技术要求**：

- 后端一个 SSE 长连接（`POST /api/v1/chat`，⚠️ SSE 用 fetch + ReadableStream，
  **不能用 `EventSource`** —— 它不支持 POST 和自定义头）
- 前端用 `@ai-sdk/react` 的 `useChat`；⚠️ **后端必须把 LangGraph 的事件翻译成
  AI SDK UI Message Stream 的 part 序列**（映射表见 [03-b §B.6.2](./03-b-技术栈-后端栈.md)）
- 翻译层单独一个模块（`agent/events.ts`），**图逻辑不许知道 SSE 存在**
- 事件类型至少：`text-delta` · `data-tool-call` · `data-pending-confirm` · `data-notice` · `finish`
- **消息的 `parts` 要落库** → 刷新后工具卡片、待确认卡片还在
  ⚠️ **落库的 parts 与推给前端的必须同源**，否则刷新后卡片内容会变
- 首字延迟目标 ≤ 2 秒（不含工具执行时间）
- **客户端断开不算错误**（记 success）—— 否则用户关页面会把错误率刷高
- 断开时要能真正停止上游调用（不能只是前端不再收）

**验收**：

- [ ] 发一句话，回答是逐字出现的（不是等完一次性出现）
- [ ] 刷新页面，工具卡片还在
- [ ] 关掉浏览器标签 → 后端请求真的终止（上游不再产生 token）
- [ ] 断网 / 后端异常 → 前端显示明确错误，不是白屏

## B2 · 会话管理 · P0

**需求**：会话能新建、列出、改名、删除、收藏、搜索。

**技术要求**：

- 首条用户消息截断自动生成标题（≤ 30 字），可手动改
- 列表按 `last_active_at` 倒序；支持分页与关键词搜索（搜标题）
- 支持「只看收藏」筛选
- 删除会话 → **级联删消息 / 工具流水 / 检查点**（不留孤儿行）
- 收藏态存会话级 + 消息级（消息级 = 对话里某一条回复打星）
- ⚠️ **切「只看收藏」这类换身份的开关，不能掐断正在流式的回答**：
  侧栏 loading 与聊天面板 loading **要拆开**；切换前要清掉「待发问题」状态
  ⚠️ 否则会出现「同一个问题被自动发两遍」—— 重复 LLM 调用 = 重复花钱
- ⚠️ **自动发送（从 URL 带问题进来）不能在 mount effect 里直接调 `sendMessage`**：
  `useChat` 在 unmount 时会 `chat.stop()`，StrictMode 下 mount effect 跑完立刻 cleanup，
  正好把 abort controller 取消掉 → **消息永远发不出去而且不报错**
  → `setTimeout(0)` 延后一拍再发
- `PATCH /sessions/:id/favorite` 不传 body = 切换

**验收**：

- [ ] 新建 / 改名 / 删除 / 收藏 / 只看收藏，全链路可用
- [ ] 删会话后 `messages` / `tool_call_logs` / `graph_checkpoints` 无残留
- [ ] 流式回答进行中点「只看收藏」→ **回答不中断**，且不重复发送
- [ ] 从 `/chat?q=xxx` 进 → 自动发一次，URL 随即 replace 成 `?session=<id>`（刷新不重复问）

## B3 · 意图识别与工具选择 · P0

**需求**：Agent 读懂用户想干什么，决定「直接答」还是「调哪个工具」。

**技术要求**：

- 判定发生在图节点 `plan`（LangGraph）：调模型 → 模型返回 tool_call 或普通文本
- **不做关键词规则匹配**（意图识别交给模型；
  规则匹配只用在「明显不需要工具」的短路上，例如纯寒暄）
- **可用工具池来自 `tools/registry.ts`**：
  内置 + Skill + MCP 三种来源统一成同一批工具给模型
- ⚠️ **工具 description 是给模型看的** —— 改 description 就是「调教模型调不调它」
- 工具太多时模型选错 → **预留按相关度裁剪工具池的扩展位**（本期不实现）
- 模型的回答与工具调用**在一次流里完成**（不要分两次请求），
  否则会出现「先回一句『我来查一下』再卡住」的两段式体验

**验收**：

- [ ] 「我桌面上有哪些文件」→ 调 `list_dir`，回答里含实际条目
- [ ] 「你好」→ 不调任何工具，直接答
- [ ] 工具不可用（被禁用 / 缺依赖）→ 模型能收到明确说明并换条路走

## B4 · 工具调用循环 · P0

**需求**：模型可以连续调多个工具，结果回灌后继续判断，直到能作答。

**技术要求**：

- 循环在 LangGraph 图内完成（`plan` → `tools` → `plan` → …），**不是**手写 while 循环
- **每一步的工具结果回灌进图状态**（不是拼进字符串），
  模型要能看到「上一次调了什么、返回了什么」
- **必须有步数上限**（默认 5，可配 `max_tool_steps`）；超限直接进 `answer`，
  并在回答里说明「已达到步数上限」
- ⚠️ **同一个工具连续重复调用要有额外限制**（默认同工具连续 2 次即停）——
  模型陷入循环时这是唯一的刹车
- **工具异常不能中断整轮**：异常转成一段「工具 X 失败：原因 Y」的文本回灌给模型，
  由模型决定下一步
- **工具调用不自动重试**（可能有副作用：写文件、发请求）——
  重试 = 执行两遍
- 工具输出**要截断**（默认 4000 字符 / 条，可配），
  超长截断并注明「已截断，共 N 字符」
- 工具输出在回灌时**标注为不可信数据**（防注入，见 [10](./10-安全方案.md)）

**验收**：

- [ ] 「把 a.txt 的 TODO 列出来再统计数量」→ 至少 2 次工具调用，结果正确
- [ ] 模型反复调同一个工具 → 在上限处停下，不烧穿预算
- [ ] 某个工具抛异常 → 整轮**不 500**；模型收到错误文本并继续
- [ ] 工具返回 1 万字 → 被截断且标注了原始长度

## B5 · 人工确认（危险操作闸门） · P0

**需求**：执行危险操作前先问用户，批准才执行，取消就不执行。

**技术要求**：

- 用 **LangGraph 的 `interrupt()`** 挂起，⚠️ **不用「前端点了再发一次请求重新跑」那种做法**
- 挂起时：**图状态落盘**（checkpointer）→ 进程重启后待确认仍在
- 前端收到 `data-pending-confirm` → 显示确认卡片（工具名 + 参数 + 风险说明）
- 用户点「批准」→ 后端用 `Command({ resume: ... })` 恢复图
- 用户点「取消」→ 恢复时把「用户拒绝了这个操作」回灌给模型，
  ⚠️ **模型不得再问第三次**（要把「已拒绝」标记进状态）
- ⚠️ **模型改了参数怎么办**：模型在恢复后重新生成 tool_call 且参数变了 → 必须**重新确认**，
  不能沿用旧的批准
- **恢复不是重新跑**：要用同一个 `thread_id` + `checkpointer` 恢复，
  之前的步骤不重跑（否则前面的工具会被执行第二遍）
- 危险档判定见 [12-c C3](./12-c-需求-工具技能与扩展.md)
- 批准 / 取消都写审计与工具流水（`status = rejected`）

**验收**：

- [ ] 触发危险工具 → 弹确认卡片，图挂起
- [ ] 点批准 → 工具**只执行一次**，图继续往下走
- [ ] 点取消 → 工具**没有执行**，模型收到「用户拒绝」，且不再追问
- [ ] 挂起后**重启后端** → 待确认的卡片仍在，批准后能正常继续
- [ ] 模型改了参数 → 重新弹确认

## B6 · 断点恢复与图状态持久化 · P0

**需求**：进程重启后，未完成的对话能从断点继续；工具调用链不丢。

**技术要求**：

- **checkpointer 必须落盘**（SQLite 表 `graph_checkpoints`），
  ⚠️ **不用进程内 MemorySaver** —— 那等于重启后状态全丢
- `thread_id` = 会话 id，一一对应
- 恢复路径：同 `thread_id` 再调一次图 → 从检查点继续
- ⚠️ **「已发出但未落库」的部分要能重放**：消息落库与图状态落库是两次写，
  顺序定为「先图状态后消息」—— 宁可重复一条消息，也不要丢图状态
- 恢复时**不重跑已完成的工具调用**（否则写文件 / 发请求会执行两遍）
- 图状态里的 `steps`（步数）、`budget_used`（已用预算）随检查点一起持久化，
  恢复后继续累计（不能因为重启就重置预算）

**验收**：

- [ ] 工具执行中 kill 进程 → 重启后该会话能继续
- [ ] 恢复后**不会重复执行**已完成的工具
- [ ] 重启后预算累计不归零

## B7 · 工具卡片与结果展示 · P1

**需求**：回答上方能看到「调了哪个工具、传了什么、返回了什么、耗时多久」。

**技术要求**：

- 工具调用以 `data-tool-call` part 落库 → 刷新后仍在
- 卡片内容：工具名 · 状态（执行中 / 成功 / 失败 / 已拒绝）· 入参 · 出参 · 耗时
- 出参**默认折叠 + 截断**（长输出不给全屏铺开）
- 失败的工具要显示**错误原因**，不吞掉
- ⚠️ **入参 / 出参里可能含敏感信息**（文件内容、token）——
  卡片默认对**密钥类字段打码**
- 多个工具调用按发生顺序排列

**验收**：

- [ ] 卡片显示状态、入参、出参、耗时
- [ ] 失败的工具显示错误原因
- [ ] 刷新后卡片内容与刷新前一致
- [ ] 密钥类字段在卡片里被打码

## B8 · 思考模式与推理预算 · P1

**需求**：用户能临时开启「思考模式」，让模型多想一会儿。

**技术要求**：

- 聊天页输入区有「思考模式」勾选框 → 请求体带 `thinking: true`
- 预算解析：`resolveThinkingBudget(模型配置, 用户勾选)`
  - 配置了 > 0 → 一直生效
  - 没配但勾了 → 兜底 1024
  - 没配也没勾 → 0
- ⚠️ **推理 token 全额算输出 token** —— UI 要能看到这部分成本
- ⚠️ **供应商不支持思考参数** → 传参报 400 时降级为「不带思考参数重试」，不报错给用户
- 思考内容**不单独展示**（模型不返回可读思考时），只体现为耗时与 token 变多

**验收**：

- [ ] 勾选思考模式 → 该轮 token 明显变多、耗时变长
- [ ] 不勾选 → 走默认预算
- [ ] 供应商不支持 → 自动降级，不报错
