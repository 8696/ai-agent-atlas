## B1 · 流式对话 · P0 🟡

**需求**：用户在 `/chat` 发消息，Agent **逐字**流式返回，工具调用过程可见。

**技术要求**：

- 后端一个 SSE 长连接（`POST /api/v1/chat`，⚠️ SSE 用 fetch + ReadableStream，
  **不能用 `EventSource`** —— 它不支持 POST 和自定义头）
- 前端用 `@ai-sdk/react` 的 `useChat`；⚠️ **后端必须把 LangGraph 的事件翻译成
  AI SDK UI Message Stream 的 part 序列**（映射表见 [03-b §B.6.2](./03-b-技术栈-后端栈.md)）
- 翻译层单独一个模块（`agent/events.ts`），**图逻辑不许知道 SSE 存在**
- 事件类型至少：`text-delta` · `data-tool-call` · `data-pending-confirm` · `data-notice` · `finish`
- **消息的 `parts` 要落库** → 刷新后工具卡片、待确认卡片还在
  ⚠️ **落库的 parts 与推给前端的必须同源**，否则刷新后卡片内容会变
- 首字延迟目标 ≤ 2 秒（不含工具执行时间）
- **客户端断开不算错误**（记 success）—— 否则用户关页面会把错误率刷高
- 断开时要能真正停止上游调用（不能只是前端不再收）

> 📌 **本期做到哪（2026-10）**：
>
> - ✅ `POST /api/v1/chat` 的 SSE 通道 + `agent/events.ts` 协议翻译层（`text-*` / `finish` / `error`）
> - ✅ 前端 `useChat` + `DefaultChatTransport`；「重试」用 `regenerate({ messageId })`
> - ❌ **还没接 LangGraph 图** —— 现在是「模型调用 + 流式出字」这一条竖切，
>   工具循环 / 人工确认闸 / 检查点属于 [B3 ~ B6](#b3--意图识别与工具选择--p0-)
> - ❌ `data-tool-call` / `data-pending-confirm` / `data-notice` 三种 part 还没产
>   （等工具集落地）；`parts` 也还没落库

**验收**：

- [x] 发一句话，回答是逐字出现的（不是等完一次性出现）
- [ ] 刷新页面，工具卡片还在
      （⚠️ **消息还没落库** —— 刷新即丢；落库是会话管理那条，见 [B2](#b2--会话管理--p0-))
- [x] 关掉浏览器标签 → 后端请求真的终止（上游不再产生 token）
      （客户端断开 → `AbortController` abort → 模型流真的停；**断开不算错误**，日志记 200）
- [x] 断网 / 后端异常 → 前端显示明确错误，不是白屏
      （聊天区出错误条 + 「重试」按钮；重试用 `regenerate({ messageId })`，**不重复发一条**）
- [x] `LLM_MODEL` 没配 → 前端显示「还没配置模型」并指明改 `.env`，不是 500
      （后端 503 + `MODEL_NOT_CONFIGURED` → 前端提示条 + 输入框禁用）

## B2 · 会话管理 · P0 ⬜

**需求**：会话能新建、列出、改名、删除、收藏、搜索。

**技术要求**：

- 首条用户消息截断自动生成标题（≤ 30 字），可手动改
- 列表按 `last_active_at` 倒序；支持分页与关键词搜索（搜标题）
- 支持「只看收藏」筛选
- 删除会话 → **级联删消息 / 工具流水 / 检查点**（不留孤儿行）
- 收藏态存会话级 + 消息级（消息级 = 对话里某一条回复打星）
- ⚠️ **切「只看收藏」这类换身份的开关，不能掐断正在流式的回答**：
  侧栏 loading 与聊天面板 loading **要拆开**；切换前要清掉「待发问题」状态
  ⚠️ 否则会出现「同一个问题被自动发两遍」—— 重复 LLM 调用 = 重复花钱
- ⚠️ **自动发送（从 URL 带问题进来）不能在 mount effect 里直接调 `sendMessage`**：
  `useChat` 在 unmount 时会 `chat.stop()`，StrictMode 下 mount effect 跑完立刻 cleanup，
  正好把 abort controller 取消掉 → **消息永远发不出去而且不报错**
  → `setTimeout(0)` 延后一拍再发
- `PATCH /sessions/:id/favorite` 不传 body = 切换
- ⚠️ **会话保留策略**：`retention_days`（默认 90 天）——
  超过则连同检查点一起清掉（对标 Hermes 的会话历史管理）

**验收**：

- [ ] 新建 / 改名 / 删除 / 收藏 / 只看收藏，全链路可用
- [ ] 删会话后 `messages` / `tool_call_logs` / `graph_checkpoints` 无残留
- [ ] 流式回答进行中点「只看收藏」→ **回答不中断**，且不重复发送
- [ ] 从 `/chat?q=xxx` 进 → 自动发一次，URL 随即 replace 成 `?session=<id>`（刷新不重复问）

## B3 · 意图识别与工具选择 · P0 ⬜

**需求**：Agent 读懂用户想干什么，决定「直接答」还是「调哪个工具」。

**技术要求**：

- 判定发生在图节点 `plan`（LangGraph）：调模型 → 模型返回 tool_call 或普通文本
- **不做关键词规则匹配**（意图识别交给模型；
  规则匹配只用在「明显不需要工具」的短路上，例如纯寒暄）
- **可用工具池来自 `tools/registry.ts`**：
  内置 + Skill + MCP 三种来源统一成同一批工具给模型
- ⚠️ **工具 description 是给模型看的** —— 改 description 就是「调教模型调不调它」
- 工具太多时模型选错 → **按相关度裁剪工具池**（本期实现）：
  - 按「工具名 + 描述」与用户当前问题的关键词/向量相关度打分
  - 取 top N（``.env` 的 `MAX_TOOLS_PER_TURN``，默认 12）+ 总是保留 `low`/`normal` 档的基础工具
  - ⚠️ **不要硬编码阈值** —— 不同嵌入模型基线差很多
- 模型的回答与工具调用**在一次流里完成**（不要分两次请求），
  否则会出现「先回一句『我来查一下』再卡住」的两段式体验

**验收**：

- [ ] 「我桌面上有哪些文件」→ 调 `list_dir`，回答里含实际条目
- [ ] 「你好」→ 不调任何工具，直接答
- [ ] 工具不可用（被禁用 / 缺依赖）→ 模型能收到明确说明并换条路走
- [ ] 工具池超过上限时，模型仍能选到最相关的那个

## B4 · 工具调用循环 · P0 ⬜

**需求**：模型可以连续调多个工具，结果回灌后继续判断，直到能作答。

**技术要求**：

- 循环在 LangGraph 图内完成（`plan` → `tools` → `plan` → …），**不是**手写 while 循环
- **每一步的工具结果回灌进图状态**（不是拼进字符串），
  模型要能看到「上一次调了什么、返回了什么」
- **必须有步数上限**（默认 5，可配 `max_tool_steps`）；超限直接进 `answer`，
  并在回答里说明「已达到步数上限」
- ⚠️ **同一个工具连续重复调用要有额外限制**（默认同工具连续 2 次即停）——
  模型陷入循环时这是唯一的刹车
- **工具异常不能中断整轮**：异常转成一段「工具 X 失败：原因 Y」的文本回灌给模型，
  由模型决定下一步
- **工具调用不自动重试**（可能有副作用：写文件、发请求）——
  重试 = 执行两遍
- 工具输出**要截断**（默认 4000 字符 / 条，可配），
  超长截断并注明「已截断，共 N 字符」
- 工具输出在回灌时**标注为不可信数据**（防注入，见 [10](./10-安全方案.md)）

**验收**：

- [ ] 「把 a.txt 的 TODO 列出来再统计数量」→ 至少 2 次工具调用，结果正确
- [ ] 模型反复调同一个工具 → 在上限处停下，不烧穿预算
- [ ] 某个工具抛异常 → 整轮**不 500**；模型收到错误文本并继续
- [ ] 工具返回 1 万字 → 被截断且标注了原始长度

## B5 · 人工确认（危险操作闸门） · P0 ⬜

**需求**：执行危险操作前先问用户，批准才执行，取消就不执行。

**技术要求**：

- 用 **LangGraph 的 `interrupt()`** 挂起，⚠️ **不用「前端点了再发一次请求重新跑」那种做法**
- 挂起时：**图状态落盘**（checkpointer）→ 进程重启后待确认仍在
- 前端收到 `data-pending-confirm` → 显示确认卡片（工具名 + 参数 + 风险说明）
- 用户点「批准」→ 后端用 `Command({ resume: ... })` 恢复图
- 用户点「取消」→ 恢复时把「用户拒绝了这个操作」回灌给模型，
  ⚠️ **模型不得再问第三次**（要把「已拒绝」标记进状态）
- ⚠️ **模型改了参数怎么办**：模型在恢复后重新生成 tool_call 且参数变了 → 必须**重新确认**，
  不能沿用旧的批准
- **恢复不是重新跑**：要用同一个 `thread_id` + `checkpointer` 恢复，
  之前的步骤不重跑（否则前面的工具会被执行第二遍）
- 危险档判定见 [12-c C3](./12-c-需求-工具技能与扩展.md)
- 批准 / 取消都写审计与工具流水（`status = rejected`）
- ⚠️ **子代理与定时任务同样走这道闸**（见 B10 / B11）——
  子代理不得绕过确认；定时任务无人值守时按「跳过并记录」处理

**验收**：

- [ ] 触发危险工具 → 弹确认卡片，图挂起
- [ ] 点批准 → 工具**只执行一次**，图继续往下走
- [ ] 点取消 → 工具**没有执行**，模型收到「用户拒绝」，且不再追问
- [ ] 挂起后**重启后端** → 待确认的卡片仍在，批准后能正常继续
- [ ] 模型改了参数 → 重新弹确认
- [ ] 子代理要调 `shell` → 同样弹确认，不自动放行

## B6 · 断点恢复与图状态持久化 · P0 ⬜

**需求**：进程重启后，未完成的对话能从断点继续；工具调用链不丢。

**技术要求**：

- **checkpointer 必须落盘**（SQLite 表 `graph_checkpoints`），
  ⚠️ **不用进程内 MemorySaver** —— 那等于重启后状态全丢
- `thread_id` = 会话 id，一一对应
- 恢复路径：同 `thread_id` 再调一次图 → 从检查点继续
- ⚠️ **「已发出但未落库」的部分要能重放**：消息落库与图状态落库是两次写，
  顺序定为「先图状态后消息」—— 宁可重复一条消息，也不要丢图状态
- 恢复时**不重跑已完成的工具调用**（否则写文件 / 发请求会执行两遍）
- 图状态里的 `steps`（步数）、`budget_used`（已用预算）随检查点一起持久化，
  恢复后继续累计（不能因为重启就重置预算）

**验收**：

- [ ] 工具执行中 kill 进程 → 重启后该会话能继续
- [ ] 恢复后**不会重复执行**已完成的工具
- [ ] 重启后预算累计不归零

## B7 · 工具卡片与结果展示 · P1 ⬜

**需求**：回答上方能看到「调了哪个工具、传了什么、返回了什么、耗时多久」。

**技术要求**：

- 工具调用以 `data-tool-call` part 落库 → 刷新后仍在
- 卡片内容：工具名 · 状态（执行中 / 成功 / 失败 / 已拒绝）· 入参 · 出参 · 耗时
- 出参**默认折叠 + 截断**（长输出不给全屏铺开）
- 失败的工具要显示**错误原因**，不吞掉
- ⚠️ **入参 / 出参里可能含敏感信息**（文件内容、token）——
  卡片默认对**密钥类字段打码**
- 多个工具调用按发生顺序排列
- ⚠️ **子代理调用单独一种卡片**（见 B10）：显示子代理名 / 任务 / 状态 / 摘要

**验收**：

- [ ] 卡片显示状态、入参、出参、耗时
- [ ] 失败的工具显示错误原因
- [ ] 刷新后卡片内容与刷新前一致
- [ ] 密钥类字段在卡片里被打码
- [ ] 子代理卡片能看出派了什么任务、返回了什么摘要

**技术要求**：

- 只看 `.env` 的 `LLM_THINKING_BUDGET`
  - 默认 **1024**（开）
  - **0 = 关**
  - 改完要重启后端
- ⚠️ **聊天页不放思考开关**

## B9 · 斜杠命令集 · P0 ⬜

**需求**：输入 `/` 开头的一行会被当成命令执行，不发给模型、不花 token。
对齐 Hermes 的会话命令集（`/new /reset /model /personality /retry /undo /compress /usage /skills /stop`）。

**技术要求**：

- **命令在服务端解析**（不是前端拦截）——
  这样历史重放、多端一致，且命令不进入模型上下文
- ⚠️ **命令不产生任何 LLM 调用**（零 token 消耗）
- 本期命令集：

  | 命令           | 作用                                                |
  | -------------- | --------------------------------------------------- |
  | `/new`         | 新建会话（等价于侧栏「新对话」）                    |
  | `/reset`       | 清空当前会话的上下文（保留历史记录与工具流水）      |
  | `/model`       | 列出可用模型；`/model <名称>` 切换本会话的模型      |
  | `/personality` | 列出可用人格文件；`/personality <SOUL 文件名>` 切换 |
  | `/retry`       | 重新生成上一轮（同 UI 的「重新生成」）              |
  | `/undo`        | 撤销上一轮（回退消息与图状态，不删会话）            |
  | `/compress`    | 手动压缩当前会话上下文（见 D1）                     |
  | `/usage`       | 本月 token / 花费 / 本会话用量                      |
  | `/skills`      | 列出已安装技能（名称 + 描述 + 来源）                |
  | `/thinking`    | `on` / `off` 思考模式开关（见 B8）                  |
  | `/stop`        | 停止当前流式输出                                    |
  | `/help`        | 列出全部命令与用法                                  |

- ⚠️ **未知命令要明确报错**：返回「未知命令 `/xxx`，`/help` 看全部」，
  **绝不把它当成普通消息发给模型**（否则会白白调一次 LLM，还可能触发工具）
- **前端补全**：输入框检测到 `/` 开头 → 弹候选列表（命令 + 已装技能名 + 模型名），
  支持 Tab 补全、上下键选择、Esc 关闭
- 命令结果按普通消息气泡渲染（但标记为「命令」样式，不进消息历史里的模型轮次）

**验收**：

- [ ] 输入 `/help` → 返回命令清单，**没有 LLM 调用**（usage 里 token 增量 = 0）
- [ ] 输入 `/usage` → 返回本月 token 与花费
- [ ] 输入 `/model` → 列出可用模型；`/model <名>` 后本会话切换成功
- [ ] 输入 `/unknowncmd` → 明确提示未知命令，**不发模型**
- [ ] 输入框打 `/` 出现补全列表，Tab 能补全

## B10 · 子代理并行 · P1 ⬜

**需求**：主 Agent 可以把子任务派给**隔离上下文的子代理**并行执行，
对标 Hermes 的 parallel subagents。

**技术要求**：

- **派发方式**：主 Agent 有一个专用工具 `spawn_subagent`：
  - 入参：`task`（子任务描述）· `name`（子代理名，可选）· `model`（可选，默认继承）
  - ⚠️ **派发本身是一次工具调用**，走统一入口与权限闸
- **子代理是隔离的图实例**：
  - 独立 `thread_id`（不共享主对话历史）
  - **独立上下文**（只拿到 `task` + 主 Agent 传的少量上下文）
  - **共用同一个工具池**与同一套权限策略
- **结果回灌方式**：子代理跑完 → 产出**一段摘要**（不是全量过程）回灌给主 Agent
  - ⚠️ **摘要必须有长度上限**（默认 2000 字符）——
    子代理的原始过程回灌主上下文会撑爆预算
- **并发控制**：``.env` 的 `SUBAGENT_MAX_CONCURRENCY``（默认 3）
  - 超过上限 → 排队，不报错
- **步数上限**：子代理独立计数，``.env` 的 `SUBAGENT_MAX_STEPS``（默认 8）
- ⚠️ **子代理不得绕过人工确认**：`shell` 等高危工具在子代理里照样要确认
  - 无人值守场景（定时任务里派发）→ 按 B11 的「跳过并记录」处理
- **独立 trace**：子代理跑一条自己的 trace（`kind='subagent'`），
  ⚠️ **不挂在主对话 trace 上**（主 trace 的 duration 保持「用户感知耗时」）
- **UI**：主对话里显示子代理卡片（名字 · 任务 · 状态 · 摘要）

**验收**：

- [ ] 「同时查 A 和 B 两件事」→ 主 Agent 派发 2 个子代理，**并行**执行
- [ ] 子代理看不到主对话的历史（只有 task）
- [ ] 子代理返回的是摘要，不是全量过程
- [ ] 并发超过上限 → 排队，不失败
- [ ] 子代理要跑 `shell` → 弹确认（不自动放行）
- [ ] 主对话 trace 的耗时不含子代理挂起等待（是主 Agent 感知耗时）

## B11 · 定时任务（cron） · P1 ⬜

**需求**：用自然语言描述周期任务，到点自动跑。对标 Hermes 的内置 cron 调度器。

**技术要求**：

- 任务描述存在 `data/cron.json`（文件，不是数据库、不是界面）
  - 每条：`name` · `schedule`（自然语言，如「每天早上 9 点」）· `prompt`（任务指令）
    · `enabled` · `sessionId`（结果写进哪个会话）· `lastRunAt`
- **自然语言 → cron 表达式**：由模型解析一次，解析结果存下来（不每次重解析）
  - ⚠️ 解析不出合法表达式 → 报错并保留原文，不静默丢弃
- **调度器**：后台每分钟检查一次到期任务（进程内定时器）
  - 走 ``.env` 的 `TIMEZONE`` 判断「今天 9 点」
  - ⚠️ **进程没跑就不会触发**（本地项目不做常驻服务保活），错过的时间点
    按「补跑一次」还是「跳过」要明确：**默认跳过**，并在日志里记「错过了 N 次」
- **执行方式**：触发时跑一次完整的图（复用同一套编排与工具池），
  结果写进 `sessionId` 指定的会话（默认一个专门的「定时任务」会话）
- ⚠️ **无人值守的确认闸处理**：任务里若触发高危工具要确认 →
  **跳过该步并记录**（「因需人工确认已跳过」），**不能挂死**
  - 可在任务里显式声明 `autoApprove: ["shell"]` 允许放行（⚠️ 高危，要显式写出来）
- ⚠️ **不做消息平台投递**（本期不做网关）→ 结果只落地到会话 + 日志 + 终端打印一行
- ``.env` 的 `CRON_ENABLED`` 总开关；任务写审计（`CRON_CREATED` / `CRON_TRIGGERED`）
- CLI 工具：`yarn cron:list` · `yarn cron:add` · `yarn cron:remove`

**验收**：

- [ ] 加一条「每天 9 点」的任务 → 到点自动跑，结果写进指定会话
- [ ] 自然语言解析不出 cron → 报错，不静默丢弃
- [ ] 任务触发时需要人工确认 → 跳过该步并记录，任务不挂死
- [ ] `yarn cron:list` 能看到所有任务与上次执行时间
- [ ] `CRON_ENABLED=false` → 调度器不触发
